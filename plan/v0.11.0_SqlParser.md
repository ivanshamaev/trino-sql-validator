# v0.11.0 Trino SQL Parser Fidelity Plan

## Goal

Make `dialect="trino"` measurably closer to Trino's own parser while preserving
the library's offline, Rust-native design and its syntax-only contract.

The v0.11.0 work is driven by a pinned upstream parser corpus, not by isolated
documentation examples alone. It must improve both sides of validation:

- accept SQL that Trino 483 accepts;
- reject malformed SQL that Trino 483 rejects;
- keep source positions and warning traversal correct after compatibility work;
- keep PrestoDB-only syntax out of the Trino dialect.

The target is parser fidelity, not semantic equivalence with a coordinator. The
library will not resolve catalogs, connector capabilities, table properties,
function overloads, privileges, or argument types.

### Superset validator proposal

Apache Superset PR
[#23852](https://github.com/apache/superset/pull/23852/files) was reviewed together
with its base `PrestoDBSQLValidator` implementation. The proposal did not add a
local Trino parser. It:

1. reused Superset's Presto validator;
2. prepended `EXPLAIN (TYPE VALIDATE)` to every split statement;
3. sent the query to a live coordinator;
4. changed only the caught driver exception from PyHive's `DatabaseError` to
   the Trino Python client's `DatabaseError`.

The PR was closed unmerged. Its review identified exactly the architectural
problem relevant here: Trino and PrestoDB had already diverged, while the reused
implementation assumed PyHive cursor behavior. The author confirmed observed
`Cursor.poll` incompatibilities and described the validator as useful but not
reliable enough in that form.

This approach can validate the exact deployed Trino version and includes
semantic analysis, connector functions, and catalog state. It also requires a
coordinator, credentials, network access, driver-specific error decoding and
query latency. It is unsuitable as this library's core parser and conflicts
with the Rust-native/offline design. A live `EXPLAIN (TYPE VALIDATE)` probe may
be used later as an opt-in development oracle, never as the default runtime
path for v0.11.0.

## How the upstream parsers work

Trino and PrestoDB both use an ANTLR4 grammar followed by an AST builder. The
grammar is only one layer of validation:

1. lexer and parser build a concrete parse tree;
2. parsing first uses fast SLL prediction, then retries in LL mode;
3. recovery is non-inserting/non-deleting so bad input is not silently repaired;
4. a postprocessor rejects empty quoted identifiers, backquotes and identifiers
   beginning with digits, and reclassifies non-reserved keywords;
5. `AstBuilder` performs additional shape and literal checks;
6. the enhanced error handler computes expected tokens at the furthest useful
   input position;
7. stack overflow is converted into a stable "statement/expression is too large"
   parsing error.

Consequently, copying `SqlBase.g4` alone would not reproduce Trino behavior.
An exact Rust port would also need the postprocessor, relevant `AstBuilder`
checks, error strategy and resource-limit behavior.

PrestoDB retains the same architecture but has materially different grammar and
options. Examples of PrestoDB-only surface include table constraints, vector
indexes, tags, `ALTER FUNCTION`, `TEMPORARY FUNCTION`, `FOR ... BEFORE`, and
identifier `@`/`:` characters. Trino instead has SQL/JSON, `MATCH_RECOGNIZE`,
`PIVOT`, `CORRESPONDING`, `NEAREST`, query-scoped session properties and
functions, SQL routine control statements, catalog DDL and broader authorization
syntax. The two corpora must therefore be compared, not unioned.

## Reproducible v0.10.0 baseline

The following audit ran the installed v0.10.0 public `validate()` API against
direct string examples extracted from the pinned Trino 483 Java tests.
Consecutive Java string literals were joined. Dynamically generated cases and
AST-only assertions were excluded.

For expression cases the audit used `SELECT <expression>`. For type cases it
used `SELECT CAST(NULL AS <type>)`.

| Corpus subset | Extracted cases | v0.10.0 matches | v0.10.0 mismatches |
| --- | ---: | ---: | ---: |
| positive statements in `TestSqlParser` | 456 | 342 | 114 |
| positive expressions in `TestSqlParser` | 232 | 212 | 20 |
| positive types in `TestTypeParser` | 68 | 47 | 21 |
| direct negative statements in `TestSqlParser` | 23 | 17 rejected | 6 accepted |
| direct-string error inputs in `TestSqlParserErrorHandling` | 57 | 40 rejected | 17 accepted |

These are lower-bound audit metrics, not claims of 75% language coverage. The

that a simple string extractor cannot execute. The error-input prototype also
treated its extracted strings through the file-level `validate()` entry point;
the committed audit tool must preserve Trino's statement versus standalone
expression entry points. Empty input is intentionally valid in this library as
a zero-statement file, whereas Trino's single-statement entry point rejects it.

The same direct-statement probe over PrestoDB 0.299 found 462 unique positive
examples: 294 happened to parse in the current Trino validator and 168 did not.
That number is diagnostic only. PrestoDB-only constructs must not become Trino
features merely to raise it.

## Findings

### 1. Regex normalization can turn invalid SQL into valid SQL

This is the highest-risk finding. `normalize_iceberg_branch_references()`
currently removes any `@` followed by an identifier anywhere in the input. The
official invalid input `@select` is therefore rewritten to an empty string and
reported as a valid zero-statement file. The same class of issue can affect
strings, comments and warning columns.

Other regex compatibility paths operate on `PREPARE`, `ARRAY`, `TOP`, typed
literals, table versions and several `VALUES` forms. Their intended syntax is
useful, but the transformation must be token-aware and restricted to a proven
grammar context.

### 2. The local lexer is more permissive than Trino

Trino's lexer permits ASCII letters or `_` at the start of an unquoted
identifier and ASCII letters, digits or `_` after it. The current local dialect
uses Unicode alphabetic characters and additionally permits `$`. It also does
not reproduce all Trino postprocessor checks. Confirmed false acceptances
include digit-leading and empty quoted identifiers.

PrestoDB explicitly permits `@` and `:` inside identifiers; that is a fork
difference and must not be copied to the Trino dialect.

### 3. Generic fallback hides statement-grammar divergence

Local token parsers cover some Trino-only statements, but several shapes reflect
older examples or permissive assumptions instead of the Trino 483 grammar. In
particular:

- `CREATE/DROP CATALOG` misses `IF NOT EXISTS`, `COMMENT`, `AUTHORIZATION`,
  `WITH (...)`, and `CASCADE`/`RESTRICT` combinations;
- branch parsing does not consistently follow the current clause order;
- `SET PROPERTIES (...)` is accepted even though Trino's statement form expects
  the property assignments without that wrapper;
- role grants/revokes miss `GRANTED BY` and `IN <catalog>` variants;
- `SET PATH` accepts more than the one- or two-part path elements allowed by
  Trino;
- `EXPLAIN VERBOSE` is accepted by Generic fallback although Trino rejects it;
- `SET SESSION AUTHORIZATION null` is accepted by fallback;
- placeholder statements prevent normal AST warning traversal.

Using `Statement::Commit` as a placeholder also blocks future statement-kind
reporting and can hide functions/types inside a recognized statement.

### 4. Query coverage is broader than the existing five-gap list

All five carried v0.10.0 query gaps now have positive, malformed-neighbor and
source-position coverage. In particular, query-scoped expression-returning
`WITH FUNCTION` declarations are parsed as synthetic `CREATE FUNCTION` AST
metadata before the following query is parsed; locally declared names are not
reported as unknown calls, while warnings inside declarations retain their
original positions.

The upstream corpus additionally exposed the following areas. The row expansion,
mixed `GROUP BY` forms, scalar relation `VALUES`, and `AT LOCAL` slices are now
covered; the remaining high-value query gap is table-function table-argument
aliases and organization clauses. Other remaining areas are:

- current `SHOW ... LIKE ... ESCAPE` and `SHOW FUNCTIONS FROM/IN` forms;
- CTAS column aliases and `WITH [NO] DATA`;
- `CREATE VIEW` comment/security/property clauses;
- qualified nested-column operations;
- current privilege and authorization object shapes.

### 5. Expression and type gaps are independently significant

Confirmed expression gaps include named static-method arguments, expression
method calls, decimal digit separators, `BETWEEN SYMMETRIC/ASYMMETRIC`, the
Trino `TRIM` variants, Unicode strings with `UESCAPE`, zero-argument lambdas,
row-pattern `RUNNING`/`FINAL` processing mode, and some quantified `VALUES`
forms.

Confirmed type gaps include parameterized time/timestamp precision identifiers,
array suffix forms, mixed angle-bracket/parenthesis containers, and interval
types with leading/fractional precision. Existing nested `ROW` support solves
an important fixture case but not the complete `TestTypeParser` surface.

### 6. SQL routines need their own parser workstream

The current `CREATE FUNCTION` compatibility parser scans forward to a single
`RETURN <expression>`. Trino 483 additionally supports:

- query-scoped `WITH FUNCTION` declarations;
- language-engine functions with `AS $$...$$` bodies;
- routine characteristics (`LANGUAGE`, determinism, null input, security,
  comment and properties);
- compound `BEGIN ... END` bodies with declarations, assignment, conditional
  and loop control statements.

The parser now accepts query-scoped expression-returning declarations and
validates each one through the same `CREATE FUNCTION` parser used for top-level
functions. It intentionally does not treat arbitrary `RETURN` text as a body:
the declaration must terminate at another `FUNCTION` or a query root. Dollar
bodies, routine characteristics, and compound bodies remain unsupported.

### 7. Negative and resource-safety coverage is too small locally

Trino tests malformed prefixes, incomplete clauses, reserved identifiers,
literal overflow, exact error coordinates, possible exponential backtracking,
and deeply nested expressions that would otherwise overflow the parser stack.
Our tests cover basic positions and a few malformed compatibility paths but not
these families systematically.

## Architecture decision for v0.11.0

Keep `sqlparser-rs` and the Rust-native extension. Do not add a JVM, Java parser,
Python SQL parser, subprocess or coordinator dependency.

Use a three-layer Trino path:

1. **Exact lexical gate and token-preserving compatibility transforms.** Never
   rewrite inside comments/literals and never remove a token unless its complete
   surrounding Trino shape has been validated.
2. **sqlparser AST for supported common syntax.** Prefer upstream dialect hooks
   and AST variants when they exist.
3. **Strict Trino-only shape parsers for missing AST variants.** They must consume
   the complete grammar shape, retain source spans needed for warnings, and
   return internal metadata rather than masquerading as an unrelated statement
   where practical.

A direct ANTLR grammar port remains a later option only if the differential
corpus proves the incremental layer unmaintainable. The threshold for revisiting
that decision is either repeated regressions caused by compatibility transforms
or inability to classify all pinned positive/negative cases without a large
parallel grammar. Apache-2.0 source may be studied and adapted with attribution,
but wholesale copied corpus or generated grammar code requires an explicit
license/NOTICE review.

## Implementation plan

## Unreleased implementation progress

The initial v0.11.0 slices are implemented in the working tree and verified by
both Rust unit tests and the public PyO3 Python API tests:

- token-safe Iceberg DML branch normalization replaces the global `@branch`
  regex and rejects residual `@` syntax;
- Trino lexical checks now reject non-ASCII and `$` unquoted identifiers,
  digit-leading identifiers, empty quoted identifiers and backquotes;
- Trino hexadecimal, octal and binary integer literals with digit separators
  are accepted without weakening adjacent identifier validation;
- query-scoped `WITH SESSION` accepts multiple expression-valued properties,
  preserves warning locations and rejects malformed property lists;
- catalog, branch, `SET PROPERTIES`, `SET PATH`, session authorization and
  `EXPLAIN` paths now enforce the relevant Trino 483 shape constraints;
- `SHOW CATALOGS/SCHEMAS/TABLES/COLUMNS/FUNCTIONS/SESSION` now handles Trino
  scope, `LIKE`, and `ESCAPE` forms with strict incomplete-clause rejection.
- `PIVOT ... GROUP BY` is accepted only after a complete top-level `FOR ... IN`
  clause inside the pivot specification. Its grouping expression is validated
  independently, then removed from the token stream without shifting warnings.
- `NEAREST (FROM ... [WHERE ...] MATCH ...)` is transformed into a correlated
  subquery only after its complete grammar shape is validated. Both predicates
  stay in the parsed AST, so function warnings and their source positions remain
  visible.
- Query-scoped `WITH FUNCTION` accepts one or more expression-returning
  declarations, parses each declaration into `CREATE FUNCTION` metadata, and
  then parses the following root query. Declaration bodies participate in
  function/type warnings with original source positions; local function calls
  are excluded from unknown-function warnings.
- Expression-qualified `ROW(...).* [AS (...)]` validates nonempty row fields
  and output aliases before replacing only the parser-incompatible shape. Each
  field is retained as parsed metadata, so nested function/type warnings keep
  their original source positions.
- `GROUP BY ALL` and `GROUP BY DISTINCT` now require a following grouping
  element and are removed as located tokens before upstream parsing, preserving
  warning positions in the selected and grouping expressions.
- `AT LOCAL` is structurally recognized and represented with a fixed generated
  timezone for syntax parsing only; incomplete `AT` and `AT TIME` forms are
  rejected without changing source locations of the value expression.
- Scalar expressions in relation-context and Trino `INSERT ... VALUES` lists are
  validated and converted to row values;
  function and type warnings remain attached to the original expressions.
- Empty `ROLLUP()` and `CUBE()` grouping elements are represented by generated
  `NULL` fields only in `GROUP BY` position. Ordinary `rollup()` calls and
  `GROUPING SETS ()` are left to their respective parser paths.
- All remaining SQL-changing compatibility paths (`PREPARE ... FROM`,
  parenthesized `ARRAY` types, `TOP` identifiers, `IPADDRESS` literals,
  Iceberg time travel, and the supported scalar/typed/array/function `VALUES`
  forms) now operate on located tokens. They do not inspect or alter comments
  and string literals, and the generated-token paths retain warning locations.
- A pre-parse Trino guard rejects unbalanced groups, a bare `CREATE TABLE`,
  incomplete `TABLESAMPLE`, numeric pseudo-typed literals, and the confirmed
  reserved-keyword `WHERE FROM` false acceptance. The full fixture inventory
  remains valid after these checks.

Against the pinned direct-string corpus, this moves positive statements from
342/456 to 354/456 and direct negative statements from 17/23 to 23/23. The
error-suite, standalone-expression and type results remain separately reported;
they are not folded into these numbers.

The follow-up audit after the token migration, `CORRESPONDING`, and `PIVOT ...
GROUP BY` support reports 361/456 accepted positive statements (up from 354/456), 52/56 rejected inputs
in the extracted error suite (up from 46/56), and 23/23 rejected direct negative
statements. The four residual error-suite differences are classified rather than

- empty input is intentionally a valid zero-statement file in this library,

- the two out-of-range `CAST(... AS BIGINT)` literals require Trino's numeric
  range validation and remain outside this syntax-only validator;
- `GROUPING(a + 2)` is an AST semantic shape restriction, not a token/grammar
  distinction.

The one remaining extracted standalone-expression difference, `1 + 1 x`, is an
audit-entry-point limitation: the public API validates statements, so the audit
wraps expressions in `SELECT`, where `x` is a legal alias. It must not be

After the additional P3 query slices, the pinned audit reports 371/456 accepted
positive Trino statements (up from 361/456), while preserving 23/23 rejected
direct negatives and 52/56 rejected error-suite inputs. The same probe accepts
293/462 PrestoDB comparison statements; this remains a divergence diagnostic,

The completed P3 table-function slice raises the pinned statement result to
373/456. Table arguments now support relation/query aliases, column aliases,

## Delivery order

1. Token-safe `@branch` handling and its positive/negative/source-position tests.
2. Differential audit tool and curated upstream regression matrix.
3. Lexical gate and false-accept cleanup.
4. Exact statement grammar corrections.
5. The five carried query gaps plus newly identified query forms.
6. Expressions/types/routines in independently releasable slices.
7. Full verification, documentation, version bump and explicitly authorized tag.

This order puts correctness before pass-rate growth: accepting one more official
query must not come at the cost of accepting malformed input or corrupting source
positions.

## Definition of done

v0.11.0 is ready when:

- the audit is reproducible from pinned source references and clearly labels its
  extracted subset;
- every extracted mismatch is classified as fixed, strict expected gap,
  intentional API difference, or documented semantic exclusion;
- all P1 false-acceptance issues are fixed;
- the carried five v0.10.0 parser gaps are either implemented with negative
  neighbors or explicitly retained as strict gaps with rationale;
- no PrestoDB-only feature is accepted intentionally under `dialect="trino"`;
- token transforms preserve literals, comments, lines and warning columns;
- all repository quality gates and fixture contracts pass;
- release notes state remaining parser and semantic limitations without claiming
  complete Trino grammar coverage.
