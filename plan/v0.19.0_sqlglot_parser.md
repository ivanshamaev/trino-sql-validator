# v0.19.0 — differential-аудит SQLGlot и точечное улучшение Trino parser

## Статус

Документ подготовлен 26 сентября 2026 года по состоянию
`trino-sql-validator 0.18.0`, commit `1e755b7`, tag `v0.18.0`.

Первичный аудит выполнен на `0.18.0`. Реализация `0.19.0` выполняется по этому
документу; итоговый статус и результаты gate фиксируются в разделе
«Результат реализации».

## Краткий вывод

SQLGlot полезен проекту как независимый parser/transpiler и источник идей, но
не как второй обязательный runtime-валидатор.

Прямое объединение результатов небезопасно:

- `ours AND sqlglot` создаёт false rejects для уже поддерживаемого Trino SQL;
- `ours OR sqlglot` снова пропускает значительную часть заведомо ошибочного SQL;
- признание `exp.Command` успешным parse не проверяет остаток statement;
- признание `exp.Command` ошибкой ломает множество корректных Trino DDL,
  security, session, `CALL`, `SHOW`, `EXPLAIN` и Iceberg statements;
- SQLGlot сам документирует, что его parser намеренно permissive, а продукт
  является transpiler, не validator.

Безопасная модель для v0.19.0:

1. оставить `validate()` и wheel/sdist независимыми от SQLGlot;
2. добавить SQLGlot только как pinned optional dependency для offline-аудита;
3. сравнивать три состояния: полноценный AST, `Command` fallback, parse error;
4. использовать Trino 483 parser tests как oracle, а не считать SQLGlot
   источником истины;
5. переносить подтверждённые улучшения в существующий Rust-native Trino path;
6. не менять `ValidationResult.valid` и warnings на основании SQLGlot.

Аудит нашёл два конкретных positive gap текущего валидатора, которые SQLGlot
обрабатывает корректно и которые подтверждены Trino 483:

```sql
CREATE TABLE foo COMMENT 'test'
WITH (string = 'bar', long = 42, computed = 'ban' || 'ana',
      a = ARRAY['v1', 'v2'])
AS SELECT * FROM t
WITH NO DATA
```

```sql
ALTER TABLE foo.t ADD COLUMN c varchar DEFAULT NULL NOT NULL
```

Их следует реализовать нативно. Подтверждённых negative cases, которые SQLGlot
отклоняет, а `trino-sql-validator` ошибочно принимает, в официальном Trino 483
corpus не найдено. Дополнительный прогон всего current-valid project corpus
через нативный `io.trino:trino-parser:483` выявил три отдельные семьи false
accepts; они включены в scope ниже независимо от SQLGlot.

## Методика аудита

### Режимы SQLGlot

Каждый SQL передавался в:

```python
sqlglot.parse(sql, read="trino", error_level=ErrorLevel.IMMEDIATE)
```

Считались два режима:

1. **Обычный SQLGlot** — любой результат без exception считается принятым,
   включая `exp.Command`.
2. **Structured mode** — результат считается принятым только тогда, когда
   parse завершился без exception и ни в одном дереве нет `exp.Command`.

`ErrorLevel.IMMEDIATE` выбран намеренно: это штатный default parser и самый
строгий из режимов немедленной обработки первой ошибки. `ErrorLevel.WARN` или
`IGNORE` для валидации использовать нельзя.

Structured mode — методика данного аудита, а не публичный strict mode SQLGlot.
`Command` означает, что SQLGlot сохранил неподдержанный statement как текст;
это не доказательство ни валидности, ни невалидности Trino SQL.

### Проверенные наборы

1. SQLGlot self-tests: `tests/dialects/test_trino.py` — 17 pytest tests и 38
   subtests, все прошли на audited commit.
2. Полный Python suite проекта: 4556 pytest tests. Runtime-трассировка всех
   обращений к Trino validator дала 4671 вызов и 4559 уникальных подготовленных
   SQL inputs.
3. Все 82 Rust unit tests. Временная test-only трассировка `parse_sql` дала 262
   уникальных SQL inputs; 126 уже встречались в pytest corpus.
4. Объединённый project-test corpus: 4695 уникальных SQL inputs.
5. Стабильный fixture corpus: 523 независимо проверяемых valid statements и
   236 независимо проверяемых invalid cases. Для основного сравнения positive
   statements проходили ту же `jinja="auto"` preparation, что публичный API;
   raw SQLGlot result измерен отдельно.
6. Direct-string и text-block corpus официальных parser tests Trino 483,
   извлекаемый существующим `tools/audit_upstream_parsers.py`.

Временная Rust/Python трассировка после измерений удалена. Повторный
`cargo test` прошёл: 82/82; рабочее дерево перед созданием этого документа было
чистым.

Важно различать два типа измерений:

- project-test corpus измеряет **обратную совместимость с текущим контрактом**;
  текущий результат библиотеки там используется как label и не является
  независимым доказательством правильности;
- positive/negative fixtures и pinned Trino 483 tests являются независимо
  проверенным syntax corpus и пригодны для сравнения корректности.

### Negative fixture

| SQLGlot outcome | Число из 236 |
| --- | ---: |

Основные SQLGlot false accepts:

- trailing, leading и doubled commas в `SELECT`, `VALUES`, `GROUP BY`,
  `ORDER BY`, function arguments и relation lists;
- `SELECT 1 == 1`;
- пустой quoted identifier;
- clause order вроде `GROUP BY ... WHERE` и `LIMIT ... ORDER BY`;
- обычный `JOIN` без `ON`/`USING`, а также `NATURAL`/`CROSS JOIN` с `ON`;
- qualified или пустой `JOIN USING`;
- unquoted reserved identifiers;
- CTE без `AS`;
- malformed window frames;
- неполные DDL, session, privilege и prepared-statement forms;
- два statements без `;` и пустые statement segments.

SQLGlot README прямо предупреждает, что parser намеренно lenient и может
принимать SQL, который отклонит реальный engine. Полученные числа соответствуют
этому назначению.

- SQLGlot снова не даёт уникального правильного rejection.

### Два подтверждённых преимущества SQLGlot

1. SQLGlot принимает документированный Trino CTAS с порядком
   `COMMENT`, `WITH`, `AS query`, `WITH NO DATA`. Наш normalizer сейчас
   ошибочно сообщает, что `CREATE TABLE` требует columns, `LIKE` или `AS`.
2. SQLGlot принимает `ADD COLUMN ... DEFAULT NULL NOT NULL`. `NULL` входит в
   Trino `literal`, но custom ALTER parser вызывает generic `parse_expr()` в
   normal state. Он поглощает следующий column constraint `NOT NULL` как
   expression `NULL NOT NULL`, после чего `parse_trino_literal` отклоняет уже
   не-literal expression. Generic column-definition path, напротив, формирует
   корректные соседние `Default(Value::Null)` и `NotNull` options.

Это единственные SQLGlot unique wins на pinned oracle. Они улучшают positive
compatibility, но не обосновывают добавление SQLGlot в runtime.

## Диагностика ошибок

На 236-case negative fixture:

- `trino-sql-validator` возвращает error для всех 236; 234 содержат
  положительные `line` и `column`, два legacy parser errors документированы;
- SQLGlot возвращает exception только для 132 cases;
- 127 `ParseError` содержат line/column/context/highlight;
- пять `TokenError` содержат source offsets, но не тот же line/column contract;
- дополнительные 22 structured rejections являются `Command`, поэтому у них
  нет syntax error и offending-token location.

SQLGlot `ParseError` удобнее для UI: в нём есть description, start/end context и
highlight. Наш публичный error компактнее и стабилен, но хранит только message,
line и column. Расширять ABI ради SQLGlot не следует. Если rich diagnostics
когда-либо понадобятся, их надо отдельно проектировать поверх source spans
native parser, не копировать нестабильную структуру exception SQLGlot.

## Дополнительный аудит нативным Trino parser

После SQLGlot-сравнения 3388 уникальных statements, которые текущая библиотека
считает valid, были по одному переданы в `io.trino:trino-parser:483` под JDK 25.
Нативный parser принял 3378 и отклонил 10. Повторная ручная классификация
отделила project compatibility от реальных false accepts.

Намеренные расхождения, которые не следует исправлять:

- BOM перед первым statement принимается как file-input compatibility;
- два `ALTER MATERIALIZED VIEW ... EXECUTE` относятся к уже принятой
  forward-compatible поддержке Trino master, отсутствующей в tag 483.

Подтверждённые false accepts:

- external `CREATE FUNCTION` и inline `WITH FUNCTION` с телом
  `AS $$return ...$$`: `AstBuilder` Trino требует, чтобы первый символ внутри
  untagged dollar body был `CR` или `LF`;
- пустые `ROLLUP()` и `CUBE()`: grammar допускает пустой список, но нативный
  AST constructor отклоняет пустой grouping set;
- unquoted `rollup()`/`cube()` как scalar call: это grammar keywords, а не
  обычные function identifiers. Quoted `"rollup"()` остаётся допустимым.

Проверены positive neighbors: dollar body с `LF` и `CRLF`, `ROLLUP(())`,
`CUBE(())`, а также quoted scalar name. Они должны остаться valid.

## Дополнительный аудит `tests/dialects/test_trino.py`

По дополнительному требованию отдельно проверен актуальный на 26 сентября
2026 года файл SQLGlot
`tests/dialects/test_trino.py` на revision
`d01e9461a7a3fcbe50a965c7a2ddf55d41aca97d`; SHA-256 файла —
`ccc5d7450c58910676c2ed999c7a12eaee8186637e09adda8a1ace3a65ecaa9f`.

Из файла извлечено 119 непосредственно заданных Trino input cases. Generator-
only проверки преобразования из Spark и ожидаемые output strings других
диалектов не являются Trino parser tests и не переносятся. Expression-only
inputs при проверке оборачиваются в `SELECT`, потому что публичный API проекта
принимает завершённые statements.

До доработки валидатор принимал 111 из этих адаптированных inputs. Восемь
расхождений были проверены через нативный `io.trino:trino-parser:483`:

- четыре формы `JSON_QUERY ... KEEP/OMIT QUOTES [ON SCALAR STRING]` валидны;
- labels `iterate:`, `leave:` и `set:` в SQL routine валидны;
- single-quoted property key в `ALTER TABLE ... SET PROPERTIES` невалиден,
  хотя SQLGlot сохраняет этот statement через permissive `Command` fallback.

В проект переносится не весь файл механически, а 27 representative positive
cases из отсутствовавших test families и пять paired negative cases. Такой
набор добавляет singular `ROW` у `FETCH`, array forms `CONCAT_WS`, JSON query
quote clauses, temporal literals с offset, расширенные `LISTAGG`, `TRIM`,
lambda у `ARRAY_FIRST`, а также недостающие combinations процедурного SQL.
Каждый перенесённый statement сначала подтверждён нативным parser Trino 483.
Источник, revision, hash и MIT-лицензия SQLGlot указаны непосредственно в
test module; runtime dependency от SQLGlot для этих regressions не требуется.

## Производительность

Локальный warmed benchmark без file I/O выполнен на 4559 уникальных SQL из
pytest runtime-трассировки. Для каждого parser сделано семь полных проходов;
ниже median:

| Parser | Median | Throughput | Время на case |
| --- | ---: | ---: | ---: |
| `trino-sql-validator 0.18.0` native extension | 0,565 s | 8069 cases/s | 123,9 µs |
| SQLGlot `main` pure Python | 1,021 s | 4466 cases/s | 223,9 µs |

В этой среде pure-Python SQLGlot был примерно в 1,81 раза медленнее. Это не
универсальный benchmark: SQLGlot предлагает `sqlglot[c]` и заявляет ускорение
своей compiled distribution относительно pure Python. Для audit dependency
compiled extra не нужен: важнее одинаковая grammar/version на всех CI runners.

## Сравнение архитектур

| Аспект | `trino-sql-validator` | SQLGlot |
| --- | --- | --- |
| Главная цель | строгая syntax validation Trino | multi-dialect parse, transform, transpile, optimize |
| Runtime | Rust + PyO3, thin typed Python API | Python; optional mypyc-compiled package |
| Базовая grammar | `sqlparser-rs` Generic + Trino guards/normalizers/custom statements | общий handwritten recursive-descent parser + Presto + Trino overrides |
| Trino-specific surface | token/source validators, normalizers, strict custom statement handlers | небольшой `Trino(Presto)` dialect и Trino parser overrides поверх общей grammar |
| Unknown statement | ошибка либо строго проверенный internal placeholder | часто `exp.Command` с необработанным остатком |
| Parse result | `ValidationResult`, statement metadata, warnings | богатый typed AST |
| Invalid SQL contract | value, exception не выходит наружу | `ParseError`/`TokenError` зависят от error level |
| Function/type names | pinned Trino catalogs, non-fatal warnings | parser в основном принимает произвольные names; это не catalog validator |
| Jinja/dbt | length-preserving project-specific masking | в audited parse path отсутствует аналогичный contract |
| Safety | token, per-statement и nesting budgets до parse | есть optional `max_nodes`, default `-1`; эквивалентные project budgets не включены по умолчанию |
| Source fidelity | normalizers сохраняют token spans и locations | rich node/error metadata, но AST generation не обещает исходное formatting/quoting |
| Dialекты | Trino target; Hive/Generic alternates | более 30 dialects и cross-dialect generation |
| Semantics | намеренно вне scope, кроме parser-time shapes и name advisories | optimizer/type/lineage utilities богаче, но parser также не заменяет engine analyzer |

SQLGlot Trino implementation на audited snapshot состоит из 26 строк dialect
configuration и 261 строки parser overrides, но опирается на большой общий
parser, Presto parser, expression hierarchy и generator. Поэтому число строк не
является мерой качества. Архитектурная разница в приоритетах: reuse и
transformation у SQLGlot против strict Trino-validation и compatibility
contracts у этого проекта.

## Где выигрывает `trino-sql-validator`

1. Существенно строже на подтверждённом negative SQL.
2. Лучше покрывает pinned Trino 483 statements, expressions и types.
3. Строго разбирает Trino/Iceberg/security/session/custom DDL вместо сохранения
   неизвестного хвоста в `Command`.
4. Поддерживает `LIMIT ALL`, `WITH SESSION`, `NEAREST`, branches/time travel,
   table functions, SQL/JSON, `MATCH_RECOGNIZE`, routines и custom types,
   которые входят в corpus проекта.
5. Не считает plugin/custom function или type name syntax error: выдаёт
   advisory warning, что соответствует границе syntax против deployment
   semantics.
6. Сохраняет действующий API: invalid SQL — значение, а не exception.
7. Имеет явные resource budgets и regression tests на panic/exhaustion.
8. Имеет точный контракт double-quoted reserved identifiers, aliases и source
   locations, выработанный по Trino grammar.
9. Не добавляет Python parser в production dependency graph и wheel startup.

## Где выигрывает SQLGlot

1. Даёт полноценный публичный typed AST с удобным обходом и заменой nodes.
2. Имеет parser, generator и transpiler для большого числа dialects.
3. Имеет formatter, optimizer, qualification, lineage и expression-building
   utilities, которых у syntax validator нет.
4. Диалекты расширяются feature flags и method overrides без token rewriting.
5. `ParseError` содержит context/highlight и поддерживает разные error levels.
6. Большой общий parser быстро получает cross-dialect syntax improvements.
7. На pinned Trino corpus корректно принимает два statements, которые текущая
   библиотека ошибочно отклоняет.
8. MIT license совместима с проектом; pure-Python base distribution не имеет
   обязательных third-party dependencies.

Эти преимущества особенно полезны для formatting, transpilation, lineage и AST
rewrites. Они не превращают SQLGlot parse success в доказательство синтаксической
валидности Trino.

## Рассмотренные варианты интеграции

| Вариант | Совместимость | Решение |
| --- | --- | --- |
| Полностью заменить `sqlparser-rs` | ломает strictness, runtime и API; теряются custom statements | отклонить |
| `valid = ours AND sqlglot` | минимум 9 false rejects на prepared positive fixtures; 123 на полном test corpus | отклонить |
| `valid = ours OR sqlglot` | 104/236 negative fixtures снова становятся valid | отклонить |
| Считать любой `Command` valid | statement body фактически не проверен | отклонить |
| Считать любой `Command` invalid | ломает 103/523 valid fixture statements и 199/484 Trino positive statements | отклонить |
| Всегда выдавать warning при disagreement | слишком шумно; меняет warning contract и native tuple ABI | отклонить |
| Публичный optional `backend="sqlglot"` | создаёт второй смысл `valid`, version drift и Python runtime parser | не включать в v0.19 |
| Offline differential audit | не меняет runtime; выявляет gaps и upstream drift | принять |
| Нативно переносить подтверждённые правила | сохраняет architecture и позволяет paired regressions | принять |

### V019-05 — правило продвижения SQLGlot-находок в validator

SQLGlot disagreement само по себе не является bug. Новый strict check можно
добавить только при одновременном выполнении условий:

1. case отклоняется официальным pinned Trino parser;
2. текущая библиотека ошибочно возвращает `valid=True`;
3. SQLGlot даёт настоящий parse/token error, а не только `Command`;
4. правило выражается в Trino grammar или parser-time `AstBuilder` contract;
5. есть positive neighbor, включая double-quoted/non-reserved варианты;
6. проверка реализуется нативно и сохраняет token spans;
7. positive fixtures, Trino corpus, Generic и Hive не получают regressions.

В текущем аудите таких candidates ноль. Поэтому v0.19.0 не должен добавлять
новые production rejections только ради согласия с SQLGlot.

## Не входит в v0.19.0

- замена `sqlparser-rs` на SQLGlot;
- новый runtime parser backend;
- изменение `valid` через consensus двух parsers;
- `ParserDisagreementWarning` в публичном result;
- публичный SQLGlot AST из `trino_sql_validator`;
- formatting, transpilation, lineage или semantic validation;
- автоматическое принятие любого SQLGlot improvement без Trino oracle;
- обновление Trino pin с 483 на master.

Если в будущем пользователям понадобится AST/transpilation, это должен быть
отдельный opt-in продуктовый proposal. Он не должен называться дополнительной
syntax validation и не должен менять строгий контракт существующего API.
