# v0.22.0 — диагностика аргументов встроенных функций

## Статус и цель

План подготовлен для выпущенной версии `0.21.0` и реализован в `0.22.0`.
Проверены публичный API, Rust-код и исходники Trino 483, revision
`50b0b50b75abd47f830b7805ee1b51716eb4065e`. После свежего native build
проходят 5 188 pytest cases, 90 Rust tests и все quality gates.

Исходная цель — обнаруживать `sum()` и `sum(a, b)` в обычных запросах,
оконных выражениях, CTE и подзапросах. После проверки Trino 483 область
расширена до 45 документированных агрегатов, включая перегруженные `min`,
`max`, `min_by` и `max_by`. Проверка остаётся ограниченной и имеет явный
режим строгости; она не обещает проверку всех сигнатур Trino.

## Воспроизведение и причина

Обратные слеши в сообщении пользователя были артефактом форматирования.
Проверен следующий SQL:

```sql
select id, date, sum() over(partition by id order by date) rn
from schema.table_name
where rn=1
;
```

`validate()` возвращает `valid=True`, `statement_count=1`, `warnings=()`.
`analyze_statements()` возвращает один `query`, строки 1–3, без ошибки.
Также без предупреждений принимаются `SELECT sum()` и `SELECT sum(1, 2)`.
Контроли `sum(1) OVER ()`, `count()`, `count(*)`, `row_number() OVER ()`
принимаются; для `my_sum()` уже выдаётся `FunctionWarning` о неизвестном имени.

Причина в `src/lib.rs::find_unknown_functions`: обход проверяет имя по
каталогу, но не читает число аргументов. `tools/extract_functions.py`
извлекает имена, а не полные сигнатуры. Это соответствует существующей
границе, описанной в AGENTS.md, README и `plan/functions-validation.md`.

Ошибка SQLGlot сама по себе не доказывает ошибку грамматики Trino.
В Trino список аргументов обычного `functionCall` необязателен, а
`AstBuilder.visitFunctionCall` не делает специальной проверки `sum`.
Исходники встроенных SUM-агрегаций требуют один SQL-аргумент. Следовательно,
`sum()` — проблема разрешения сигнатуры на этапе анализа, а не синтаксиса.
`OVER (...)` не добавляет аргументы к вызову.

Источники, проверенные при подготовке:

- [Trino 483 grammar: functionCall](https://github.com/trinodb/trino/blob/50b0b50b75abd47f830b7805ee1b51716eb4065e/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4#L640-L643).
- [AstBuilder: обычные и parser-special вызовы](https://github.com/trinodb/trino/blob/50b0b50b75abd47f830b7805ee1b51716eb4065e/core/trino-parser/src/main/java/io/trino/sql/parser/AstBuilder.java#L3199-L3324).
- [Документированная сигнатура sum(x)](https://github.com/trinodb/trino/blob/50b0b50b75abd47f830b7805ee1b51716eb4065e/docs/src/main/sphinx/functions/aggregate.md#L355-L357).
- [BigintSumAggregation](https://github.com/trinodb/trino/blob/50b0b50b75abd47f830b7805ee1b51716eb4065e/core/trino-main/src/main/java/io/trino/operator/aggregation/BigintSumAggregation.java#L33-L39).
  Дополнительно проверены Decimal, Double, Real, Number, IntervalDayToSecond
  и IntervalYearToMonth SUM: у каждой входной функции один SQL-аргумент.
  Служебные state/block-index параметры Java не являются SQL-аргументами.

Нативный Java parser oracle и живой координатор для этого исследования
не запускались. Вывод о границе parser/analyzer основан на исходниках;
его нельзя записывать как результат выполненного engine-теста.

## Отдельная проблема: `WHERE rn=1`

Алиас `rn`, объявленный в текущем `SELECT`, не становится входной колонкой
его `WHERE`. В [StatementAnalyzer](https://github.com/trinodb/trino/blob/50b0b50b75abd47f830b7805ee1b51716eb4065e/core/trino-main/src/main/java/io/trino/sql/analyzer/StatementAnalyzer.java#L3482-L3488)
`WHERE` анализируется в области исходных отношений.

Если в `schema.table_name` есть колонка `rn`, ссылка может разрешиться в неё.
Если такой колонки нет, возникнет ошибка разрешения имени. Без схемы таблицы
нельзя объявлять ошибкой всякое совпадение имени в `WHERE` и алиаса `SELECT`.
Проверка видимости колонок не входит в обязательный объём этого релиза.

Если нужен первый ряд по дате внутри `id`, запрос можно записать так:

```sql
WITH ranked AS (
    SELECT id, date,
           row_number() OVER (PARTITION BY id ORDER BY date) AS rn
    FROM schema.table_name
)
SELECT id, date, rn
FROM ranked
WHERE rn = 1;
```

При одинаковых датах для определённого выбора строки нужен дополнительный
ключ сортировки. Если требуется именно сумма, следует передать выражение
в `sum(...)` и также фильтровать её результат во внешнем запросе.

## Реализованный контракт API

Во все три публичные функции добавлен keyword-only параметр:

```python
function_arguments: Literal["off", "warn", "error"] = "warn"
```

| Режим | Синтаксически корректный `sum()` в Trino |
| --- | --- |
| `off` | Поведение 0.21.0: `valid=True`, новой диагностики нет |
| `warn` (по умолчанию) | `valid=True`, новый `FunctionArgumentWarning` |
| `error` | `valid=False`, `Error` на имени функции |

По умолчанию `valid` сохраняет синтаксический смысл. Клиент, которому нужен
отрицательный `valid` для этого случая, явно выбирает `error`.
Документация и пример вывода должны показывать предупреждения: вывод только
`valid`/`statements` по-прежнему не показывает все результаты проверки.

В `hive`/`generic` Trino-правила не запускаются при любом режиме.
Неизвестное значение режима вызывает `ValueError` как ошибка использования
API. Невалидный SQL и нарушение правила никогда не вызывают исключение.
Настоящая ошибка парсинга имеет приоритет над проверкой аргументов.

Реализованная frozen dataclass:

```python
@dataclass(frozen=True)
class FunctionArgumentWarning:
    name: str
    actual_count: int
    expected_counts: tuple[int, ...]
    line: int | None = None
    column: int | None = None
```

Для исходного примера: `name="sum"`, `actual_count=0`,
`expected_counts=(1,)`, `line=1`, `column=18` (начало `sum`).
Сообщение: `Trino built-in function 'sum' expects 1 argument; got 0`.
В режиме `error` использовать префикс `function argument error:`, а не
`sql parser error:`. Сохранить текущий контракт invalid-result:
`statement_count=0`, `warnings=()`, одна первая ошибка по исходной позиции.
`analyze_statements()` сохраняет source-derived сведения о statements и
выставляет соответствующий `error_statement_index`.

## Логика реализации

### 1. Отдельный реестр проверенных правил

Добавлен Rust-модуль `src/function_arguments.rs`. Реестр содержит 45
документированных aggregate names с конечными наборами допустимых количеств
обычных positional expressions. Это ограниченный проверенный набор, а не
автоматическое заключение по всем 472 именам каталога.

| Допустимое число аргументов | Функции |
| --- | --- |
| `{1}` | `any_value`, `arbitrary`, `array_agg`, `avg`, `bitwise_and_agg`, `bitwise_or_agg`, `bitwise_xor_agg`, `bool_and`, `bool_or`, `checksum`, `count_if`, `every`, `geometric_mean`, `histogram`, `kurtosis`, `map_union`, `merge`, `approx_set`, `skewness`, `stddev`, `stddev_pop`, `stddev_samp`, `sum`, `variance`, `var_pop`, `var_samp` |
| `{2}` | `corr`, `covar_pop`, `covar_samp`, `map_agg`, `multimap_agg`, `regr_intercept`, `regr_slope` |
| `{3}` | `approx_most_frequent` |
| `{4}` | `reduce_agg` |
| `{0, 1}` | `count` |
| `{1, 2}` | `approx_distinct`, `min`, `max`, `tdigest_agg` |
| `{2, 3}` | `approx_percentile`, `min_by`, `max_by`, `numeric_histogram` |
| `{1, 2, 3}` | `qdigest_agg` |

Источник — все function directives в Trino 483 `aggregate.md`, включая
повторную сверку `approx_set`, `merge`, `qdigest_agg` и `tdigest_agg` с
профильными страницами HyperLogLog/QDigest/TDigest. Для `count` проверяются
ноль или одно обычное expression; `count(*)` пропускается как wildcard.
`listagg` исключён: optional separator, overflow clauses и обязательный
`WITHIN GROUP` требуют отдельной структурной проверки.

Не изменять вручную `src/functions.rs`, `src/types.rs` и manifests.
Не пытаться получить arity простым подсчётом запятых в документации:
в сигнатурах встречаются optional/variadic параметры и вложенные типы.
Для небольшого отдельного реестра хранить provenance в плане и тестовом
корпусе; если позже потребуется генерация, добавлять её отдельным шагом.

### 2. Отбор вызовов и подсчёт

После успешного Trino parse обойти `Expr::Function`:

1. Проверить, что вызов исходный, а не синтетическая конструкция normalizer.
2. Применять правило только к однокомпонентному имени из реестра, без учёта
   регистра. Quoted имена, qualified calls и method/static method calls
   пропускать: совпадение текста имени недостаточно без name resolution.
3. Исключить unqualified имя, объявленное через inline `WITH FUNCTION`
   в соответствующей области. Объявление из другого statement не исключает
   проверку. При неясной принадлежности пропустить правило, не угадывать.
4. Для `FunctionArguments::List` считать элементы `args`, а не дочерние
   AST-узлы или запятые. `sum(coalesce(x, 0))` имеет один аргумент;
   `sum((a, b))` также имеет один аргумент, хотя тип может быть неподходящим.
5. `DISTINCT`/`ALL`, `FILTER`, `OVER`, window `PARTITION BY`/`ORDER BY`,
   aggregate-local `ORDER BY` не входят в число аргументов. Вложенные вызовы
   при этом проверять независимо.
6. Named arguments, wildcard (`sum(*)`, `sum(t.*)`), нестандартные формы
   `FunctionArguments` и неоднозначные transformed calls считать
   неподдержанными этим правилом. Не выдавать ложное «0 аргументов» и не
   обещать проверку их допустимости. `sum(*)` — отдельное будущее правило
   формы аргумента, не проверка количества expressions.
7. Если число обычных аргументов не входит в набор реестра, сформировать
   диагностику со всеми допустимыми количествами.

Не запрещать все вызовы с пустыми скобками: `row_number()`, `rank()`,
пользовательские функции и другие допустимые нуль-аргументные вызовы
должны сохранить поведение. `count()`/`count(x)` проверяются как допустимые,
`count(*)` пропускается как wildcard, а `listagg` остаётся отдельным контролем
вне реестра.

### 3. Обход, нормализация и области видимости

Интегрировать проверку в `validate_sql_inner` после успешного разбора и
до сборки итогового результата, отдельно от `validate_trino_ast`.
Обе ветки Trino parsing (быстрая и с дополнительными normalizers) должны
приводить к одному запуску проверки. Сохранить budgets и panic containment.

Обойти основной AST, CTE, вложенные SELECT/EXISTS, query внутри DML/DDL
и wrappers, тела inline functions и `compatibility_metadata`. Для проверки
самого вызова агрегата не требуется знать число выходных колонок CTE.

`compatibility_metadata: Vec<Statement>` не хранит полную область видимости
inline declarations. Поэтому metadata проверяется с консервативным общим
набором имён inline functions: если имя из реестра объявлено локально хотя бы
в одном statement ввода, сомнительные metadata-вызовы пропускаются. Основной AST
сохраняет точную query scope. Представление metadata по-прежнему сохраняет
существующие function/type warnings.

Позиция берётся из original function identifier span, не из повторного
поиска текста функции. Дедупликация по rule/name/source span; разные вызовы
с одинаковым именем остаются отдельными. Диагностики сортируются по позиции.
Не клонировать/раскрывать CTE для каждого использования; обход ограничен
размером разобранного представления и существующими лимитами входа.

### 4. Python/native ABI и шаблоны

Добавить режим в native `validate`, `validate_file`, `analyze_statements`
и передавать его до Rust-проверки. Предусмотреть options-aware внутренние
функции; сохранить используемые Rust/fuzz entry points с документированным
default mode. Проверка Python не должна реализовывать SQL-анализ.

Предлагаемое расширение единого native warning tuple:

```text
(kind, name, line, column, actual_count?, expected_counts?)
```

Новый kind — `function_arguments`; для старых warnings два новых поля
равны `None`. Одновременно обновить Rust alias и все producers,
Python `_NativeWarning`/converter, `_native.pyi`, `__all__`, union
`ValidationResult.warnings` и тесты прямого native API. Сам внешний
`ValidationResultTuple` остаётся шестипольным. Старые warning dataclasses
и свойства `unknown_functions`/`unknown_types` сохраняют смысл.

Jinja-маска не является достоверным списком аргументов после рендеринга:
`sum({{ args }})` может раскрыться в несколько аргументов, а `{% ... %}`
меняет структуру запроса. Для первого релиза при изменении SQL существующей
маской отключать новую проверку для всего данного ввода, включая `error`.
Не отключать синтаксическую проверку и старые diagnostics; сохранять длину
и переводы строк. Явно документировать это ограничение и рекомендовать
проверять отрендеренный SQL. Более точное отслеживание template spans
остаётся отдельной задачей. В native API для обычного SQL маскирования нет.

## План тестов

Добавить Rust unit tests и `tests/test_v022_function_arguments.py`.
Тесты должны различать parser validity, advisory и strict результат.

| Сценарий | Ожидаемое поведение новой проверки |
| --- | --- |
| Точный запрос пользователя | Одна диагностика `sum`, 1:18; в режиме `warn` — `valid=True`, в `error` — `valid=False` |
| `sum()`, `sum(1, 2)`, включая `OVER` | Counts 0/2; в `off` сохранено 0.21.0 |
| `min()`, `max(a,b,c)` | Diagnostics с `expected_counts=(1, 2)` |
| `min(x)`, `min(x,n)`, `max(x)`, `max(x,n)` | Обе документированные arity принимаются |
| Все 45 имён реестра | Каждая разрешённая arity принимается, а число выше максимального диагностируется |
| Все имена, кроме `count` | Пустой вызов диагностируется |
| `count()`, `count(x)`, `count(*)` | Первые два допустимы; wildcard пропускается |
| `listagg(...)` | Специальная форма остаётся вне общего positional registry |
| `sum(1)`, `sum(DISTINCT x)`, `sum(coalesce(x, 0))` | Нет новой диагностики |
| `sum(x) FILTER (WHERE x > 0)` и `sum(x) OVER (...)` | Clauses не добавляют аргументы |
| `sum(sum())` | Только внутренний вызов нарушает правило количества |
| CTE, scalar subquery, CTAS, INSERT SELECT, EXPLAIN, PREPARE | Вызов находится внутри каждого поддержанного контейнера |
| Inline function с именем `sum`, metadata, соседний statement | Нет утечки exemptions между областями и statements |
| Qualified `catalog.schema.sum()`, static methods | Нет применения правила по одному suffix |
| `sum(*)`, `sum(t.*)`, named arguments | Не классифицируются ошибочно как пустой positional call |
| `count()`, `count(*)`, `row_number()`, `rank()`, `my_sum()` | Нет новых ошибок arity; старые warnings сохранены |
| `sum('text')`, `sum((1, 2))` | Один аргумент; типы не проверяются |
| LF, CRLF, комментарии, Unicode перед именем | Точные original line/column |
| Несколько вызовов/statement, repeated metadata | Сортировка, отсутствие дублей, верный error index |
| Неизвестный режим, hive/generic, validate_file | API и согласованное поведение всех entry points |
| Jinja expression/control tags и уже rendered SQL | Маска не становится источником ложной arity-ошибки |
| Ошибка синтаксиса рядом с `sum()` | Приоритет parser error |

Для `WHERE rn=1` добавить два защитных примера: исходная таблица с неизвестной
схемой и self-contained `VALUES` с реальной входной колонкой `rn`.
Одна лишь совпадающая SELECT alias не должна создавать новую ошибку.
Исправленный запрос с внешним фильтром и `row_number()` — positive control.

Нативный parser oracle и живой coordinator при реализации не запускались.
Граница parser/analyzer подтверждена grammar и Java-исходниками Trino 483,
а допустимые количества — закреплённой документацией функций и source-level
реализациями `count`. SQLGlot не использовался как analyzer oracle; JVM/сервер
не добавлялись в runtime или default tests.

В parser-аудитах явно использовать `function_arguments="off"`, а новый
semantic corpus вести отдельно. Не менять parser-метки ради совпадения
с `error` mode. Проверить fixture inventory: новые default warnings требуют
точечных reviewed expectations, не массового подавления предупреждений.
