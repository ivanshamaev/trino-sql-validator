# v0.6.0 Plan: Trino recursive CTEs and backslash literals

## Findings

The reported `CAST('\\' AS VARCHAR)` failures were caused by the custom Trino
Dialect inheriting an escape setting that treats `\\` as a string escape. Trino
uses backslash as ordinary string content in this form, so the dialect must
leave backslash escaping disabled. The parser then accepts a one-character
backslash literal and keeps the SQL semantics aligned with Trino.

The reported `WITH RECURSIVE` forms do not reproduce with the pinned
`sqlparser 0.62`: recursive CTEs are accepted both at statement scope and
inside `FROM (...)` subqueries, including named column lists. No textual
normalization is needed or desirable because it could alter CTE scope or AST
positions.

## Implementation in v0.6.0

- Set `TrinoDialect::supports_string_literal_backslash_escape()` to `false`.
- Add regression coverage for `CAST('\\' AS VARCHAR)`.
- Add regression coverage for recursive CTEs at top level and in nested
  subqueries, with and without a CTE column list.
- Keep unsupported recursive grammar cases visible as parser errors instead of
  accepting them through a permissive preprocessor.

## Verification

Run `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets -- -D warnings`,
`pytest -q`, `ruff check .`, and `mypy python/trino_sql_validator`.

## Follow-up if upstream examples still fail

If a specific production query still fails, add the exact SQL as a local
fixture and classify the failure before changing the parser. The likely next
step is a narrow `TrinoDialect` parser override for that grammar shape, not a
blanket removal of recursive-CTE validation.
