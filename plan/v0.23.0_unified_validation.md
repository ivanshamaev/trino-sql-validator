# v0.23.0 — ошибки и все предупреждения в обычном вызове

## Цель и причина

Обычный `validate(sql)` должен выполнять существующие проверки и одновременно
возвращать отрицательный `valid` при неверном количестве аргументов и полный
список диагностик. Пользователю не требуется выбирать между `warn` и `error`
или вызывать библиотеку дважды.

В 0.22.0 оба режима собирают одинаковые данные в `validate_sql_inner`.
Однако ветка `Error` возвращает `Vec::new()` вместо собранных warnings;
ветка `Warn` сохраняет диагностики, но всегда возвращает `valid=True` после
успешного разбора. Воспроизведено на установленной 0.22.0:

| Ввод | `warn` | `error` |
| --- | --- | --- |
| Два statement с `sum()` и `min()` | `valid=True`, две диагностики | `valid=False`, первая ошибка, пустые warnings |
| `SELECT sum(), my_missing_fn(), CAST(1 AS missing_type) AS over; SELECT min()` | Пять диагностик всех четырёх видов | `valid=False`, все пять диагностик потеряны |

## Контракт 0.23.0

После успешного синтаксического разбора собрать все диагностики для всех
statement, CTE, подзапросов, inline declarations и compatibility metadata.
Определять итоговую валидность только после этого обхода.

- Во всех Python/native/Rust entry points default — `error`.
- При нарушении арности `valid=False`, `error` содержит первую ошибку арности
  по исходной позиции, `warnings` содержит все собранные диагностики, включая
  эту первую ошибку в форме `FunctionArgumentWarning`.
- `function_argument_warnings` возвращает все нарушения арности; остальные
  свойства (`unknown_functions`, `unknown_types`, `ambiguous_aliases`) также
  доступны при `valid=False`.
- Самостоятельные `FunctionWarning`, `TypeWarning`, `AliasWarning` остаются
  advisory: неизвестное каталогу имя не доказывает ошибку на конкретном сервере.
- Для совместимости `statement_count=0` при отрицательном результате.
  `analyze_statements()` по-прежнему возвращает все source-derived statements
  и индекс statement с первой ошибкой. Для двух запросов пользователя это
  два `StatementInfo` и `error_statement_index=0`.
- При ошибке парсинга, превышении budget или перехваченном panic полного AST
  нет: `valid=False`, parser error и пустые warnings. Частичное восстановление
  разбора не входит в этот релиз.

Пример целевого поведения:

```python
result = validate("SELECT sum(); SELECT min()")
assert not result.valid
assert result.error is not None
assert [w.name for w in result.function_argument_warnings] == ["sum", "min"]
```

Имя `FunctionArgumentWarning` сохраняется ради совместимости. `warnings` —
канал подробных диагностик, который теперь может быть непустым одновременно
с `error`. Проверять успешность следует через `valid` или `bool(result)`.
`repr(result)` должен показывать количество диагностик и при `valid=False`.

## Совместимость и ограничения

Существующий необязательный параметр сохраняется; новый режим `both` не нужен:

| Вызов | Нарушение арности | Диагностики |
| --- | --- | --- |
| `validate(sql)` | `valid=False` | Все |
| `validate(sql, function_arguments="error")` | `valid=False` | Все |
| `validate(sql, function_arguments="warn")` | `valid=True`, если parse успешен | Все |
| `validate(sql, function_arguments="off")` | Не проверяется | Остальные существующие warnings |

`warn` и `off` — явные настройки совместимости для вызывающего кода;
обычный вызов включает и строгую проверку арности, и сбор всех warnings.
Изменение default и непустые warnings у invalid-result отметить в CHANGELOG.

Реестр остаётся тем же: 45 агрегатов из 0.22.0. Сохраняются границы quoted/
qualified calls, wildcard/named arguments, inline functions и Trino-only
проверки. Если Jinja-маска меняет ввод, выводить арность по маске по-прежнему
нельзя; проверять отрендеренный SQL. Видимость `WHERE rn=1`, позиции
GROUP BY/ORDER BY, типы аргументов и полное разрешение сигнатур — отдельные задачи.

## Логика изменения

1. В `src/lib.rs::validate_sql_inner` сохранить существующий полный сбор issues
   и предупреждений. Отсортировать и дедуплицировать issues; сохранить первую
   ошибку для `Error`, затем преобразовать все issues в warning tuples при
   любом режиме кроме `Off`. Отсортировать/дедуплицировать общий список до
   формирования результата. Возвращать его также в ветке ошибки арности.
2. Изменить default в трёх `#[pyfunction]`, `validate_sql_impl`,
   `validate_sql_unchecked`, `analyze_sql_impl`, трёх Python wrapper-функциях и
   `_native.pyi`. Options-aware Rust entry points сохраняют явный режим.
3. Сохранить существующие шестипольные native tuples, dataclasses, свойства
   и преобразование Rust → Python. Python wrapper не принимает решений о
   валидности SQL. Обновить docstrings и invalid-ветку `__repr__`.
4. В `tools/audit_upstream_parsers.py::probe` явно использовать
   `function_arguments="off"`: это сравнение с парсером Trino. В 0.22.0
   документация уже предлагала этот режим, но фактически tool вызывал
   `validate(sql)` без него. Добавить проверку, что `SELECT sum()` остаётся
   parser-positive в этом аудите, но invalid в обычном публичном API.
   Не менять baseline ради semantic-rejections; остальные parser corpora
   проверять с учётом их явно заявленного назначения.
5. В fuzz target `warnings` проверять payload независимо от `valid`:
   invalid-result теперь тоже содержит диагностики. Проверить поля количества
   аргументов и отсутствие нарушения арности в успешном default-result.
6. Синхронизировать версии Cargo.toml/pyproject.toml и оба Cargo.lock до 0.23.0,
   обновить README, CHANGELOG, AGENTS и описания границ в plan/.

## Проверки и критерии готовности

- Точный многострочный скрипт пользователя: обычный вызов invalid; сохранены
  `sum` в 1:18 и `min` в 5:18. Строгий и предупредительный режимы возвращают
  одинаковый полный набор диагностик, отличаясь `valid`/`error`/count.
- Смешанный пример: сохранены обе ошибки арности и Function/Type/Alias warnings,
  в исходном порядке. Если warning расположен раньше нарушения арности,
  `error` всё равно указывает на первое нарушение арности.
- Несколько одинаковых вызовов в разных позициях не склеиваются; повторное
  представление в metadata не дублирует диагностику.
- `validate`, `validate_file` (в том числе `jinja="reject"`),
  `analyze_statements` и прямой `_native` согласованы.
- Нативные Rust default/explicit entry points согласованы; parser budgets
  и panic containment не обходятся.
- Положительные arity для всех 45 имён сохранены; неверные пустые/избыточные
  вызовы в существующей матрице invalid по умолчанию и содержат диагностики.
- Explicit `warn`/`off`, Generic/Hive, Jinja, inline scopes, CTE и metadata
  сохраняют прежние границы.
- Ошибка синтаксиса рядом с `sum()` имеет приоритет; invalid syntax не получает
  выдуманных частичных diagnostics.
- После fresh native build: fmt, clippy `-D warnings`, cargo test, pytest,
  Ruff, mypy, no-PyO3 core, fuzz compile и pinned parser audit.
- Для изменения только политики generated catalogs не регенерировать.
  Числа тестов и статус исполнения записать после фактического прогона.
