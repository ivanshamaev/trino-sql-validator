## Общий план

Задача разбивается на два независимых слоя: **ядро на Rust** (лексер + парсер + AST + проверка ошибок) и **Python-биндинги** (интерфейс вызова). Ключевой вопрос — откуда брать грамматику Trino SQL, потому что от этого зависит скорость разработки, полнота покрытия и производительность.

### Шаг 1. Определить, что значит "корректный код"

Нужно сразу решить объём проверки, иначе легко провалиться в бесконечный скоуп:

- **Только синтаксис** (быстро, реалистично): парсинг без ошибок = валидный SQL. Не проверяет существование таблиц/колонок, типы, доступность функций.
- **Синтаксис + базовая семантика**: резолвинг имён функций, проверка количества аргументов, базовая типизация литералов — сложнее и требует каталога метаданных (Trino-специфичные функции, коннекторы).

Для "быстро проверять код" почти наверняка нужен **первый вариант** — чисто синтаксический валидатор, как линтер. Семантическую проверку (существуют ли таблицы) без реального коннектора к Trino всё равно не сделать корректно.

### Шаг 2. Выбор источника грамматики (главное архитектурное решение)

Три пути:

**A. Сгенерировать парсер из официальной ANTLR4-грамматики Trino (`SqlBase.g4`)**
- Trino использует ANTLR4 для своего SQL-парсера, грамматика открыта в репозитории trino.
- В Rust есть `antlr4rust` runtime — можно сгенерировать лексер/парсер из `.g4` файла и получить парсер, который **1:1 повторяет реальный Trino-парсер**, включая все синтаксические расширения (UNNEST, LAMBDA, ROW, MATCH_RECOGNIZE и т.д.).
- Плюсы: максимальная точность и покрытие "из коробки", легко обновлять при выходе новых версий Trino (перегенерировать из нового `.g4`).
- Минусы: ANTLR-парсеры на Rust не самые быстрые (накладные расходы рантайма ANTLR), плюс генерируемый код довольно тяжеловесный.

**B. Взять существующий Rust SQL-парсер (`sqlparser-rs`) и адаптировать/форкнуть под диалект Trino**
- `sqlparser-rs` уже поддерживает несколько диалектов (Postgres, MySQL, Snowflake, Hive и т.д.), но диалекта Trino там нет, и многие Trino-специфичные конструкции придётся добавлять руками.
- Плюсы: готовая быстрая инфраструктура (ручной lexer+recursive descent parser, без ANTLR runtime), большое комьюнити.
- Минусы: придётся дописывать и поддерживать diff с апстримом, риск разойтись с реальным поведением Trino по редким конструкциям.

**C. Написать свой парсер с нуля (ручной lexer + `lalrpop`/`pest`/чистый recursive descent) по мотивам грамматики Trino**
- Максимальный контроль и производительность (нет накладных расходов сторонних рантаймов).
- Минусы: самый долгий путь, высокий риск разойтись с оригинальной грамматикой Trino (пропустить нюансы), придётся самому поддерживать соответствие новым версиям Trino.

### Рекомендуемый путь

Гибридная стратегия, которая закрывает и скорость разработки, и производительность:

1. **Старт с варианта A** (ANTLR4 → antlr4rust) — это даст рабочий, полностью корректный по покрытию валидатор быстрее всего, так как грамматика уже написана и поддерживается командой Trino. Это особенно ценно, раз у вас уже есть внутренняя библиотека парсинга Trino — можно свериться с ней или переиспользовать наработки по тестовым SQL-конструкциям.
2. **Профилировать** и, если ANTLR-рантайм даёт неприемлемую задержку на горячем пути (валидация в проде/CI на больших объёмах запросов), — переписать именно узкое место (обычно лексер, реже сам парсер) на ручной Rust-код (`logos` для лексера — он один из самых быстрых в экосистеме), оставив грамматику как эталон поведения для тестов.
3. Держать ANTLR-версию как **источник истины для тестов** (differential testing): для каждого SQL из вашего тестового набора (~150 конструкций, которые вы уже готовите) сверять результат ручного/оптимизированного парсера с ANTLR-версией.

### Шаг 3. Архитектура крейтов

```
trino-sql-core/      # лексер, парсер, AST, единая функция validate(sql: &str) -> Result<(), Vec<SyntaxError>>
trino-sql-py/        # PyO3-биндинги поверх core
```

- `trino-sql-core` — чистый Rust, без зависимостей от Python, тестируется отдельно (`cargo test`, fuzzing).
- `trino-sql-py` — тонкий слой на `PyO3` + сборка через `maturin`.

### Шаг 4. Python-биндинги

- **PyO3 + maturin** — стандарт для Rust-библиотек в Python, лучшая производительность и поддержка типов (генерация `.pyi`-стабов).
- API минимальный:
  ```python
  import trino_sql_validator as tsv

  ok, errors = tsv.validate(sql_text)
  # errors: список (line, column, message)
  ```
- Для батч-проверки (много запросов) — освобождать GIL (`py.allow_threads`) и параллелить через `rayon` внутри Rust, а не через Python `multiprocessing`.
- Возвращать структурированные ошибки (позиция + сообщение), а не просто bool — иначе пользы для линтинга/IDE будет мало.

### Шаг 5. Производительность

- Избегать лишних аллокаций: работать со срезами `&str` вместо копирования строк в AST, где возможно.
- Арена-аллокатор (`bumpalo`) для узлов AST — резко снижает нагрузку на аллокатор при парсинге больших запросов.
- Если ANTLR-рантайм окажется узким местом — это обычно первое, что переписывается вручную.
- Бенчмаркинг с `criterion` с самого начала, на реальных запросах разного размера (короткие DML, длинные CTE/DDL из Iceberg).

### Шаг 6. Тестирование и валидация корректности

- Использовать уже собираемый вами набор ~150 валидных Trino/Iceberg SQL конструкций как smoke/regression-тесты.
- Дополнительно — набор **заведомо невалидных** запросов (опечатки, незакрытые скобки, неверные ключевые слова) для проверки, что парсер их действительно отклоняет.
- Fuzzing (`cargo-fuzz` / `arbitrary`) на входных строках — полезно для парсеров, чтобы ловить паники/зависания.
- Если есть доступ к реальному Trino coordinator — differential testing: гонять те же запросы через `EXPLAIN` в Trino и сверять, что решение "валидно/невалидно" совпадает.

### Шаг 7. Дистрибуция

- Сборка через `maturin build --release` с `manylinux`/`macos`/`windows` wheels в CI (GitHub Actions с `maturin-action`).
- Публикация во внутренний PyPI-репозиторий компании (раз библиотека внутренняя).

---

**Итог:** начинайте с генерации парсера из официальной ANTLR4-грамматики Trino через `antlr4rust` — это даст быстрый старт с максимальным покрытием синтаксиса. Оптимизируйте руками только те части, которые профилирование покажет как узкое место, а саму грамматику держите эталоном для регрессионных тестов.


# Технический план реализации

## Фаза 0. Подготовка (1 неделя)

**Цели:**
- Зафиксировать скоуп: чисто синтаксическая валидация (без резолвинга схем/таблиц/функций).
- Получить актуальную грамматику Trino: клонировать репозиторий `trinodb/trino`, найти `SqlBase.g4` (обычно в `core/trino-parser/src/main/antlr4/...`).
- Зафиксировать версию Trino, под которую ориентируемся (грамматика меняется между релизами).

**Результат:** зафиксированный `.g4`-файл в репозитории проекта + документ с описанием скоупа (что считается "ошибкой", а что нет).

---

## Фаза 1. Core-парсер на Rust (2–4 недели)

### 1.1. Генерация парсера из ANTLR-грамматики
- Установить `antlr4` (Java, для генерации) и `antlr4rust` runtime.
- Настроить `build.rs`, который на этапе сборки прогоняет ANTLR по `SqlBase.g4` и генерирует Rust-код лексера/парсера/visitor'ов.
- Проверить, что генерируемый код собирается и парсит простейший `SELECT 1`.

### 1.2. Обёртка над сгенерированным парсером
- Написать модуль `trino_sql_core::parser`, который:
  - принимает `&str`,
  - прогоняет через лексер → парсер,
  - собирает **все** синтаксические ошибки через кастомный `ErrorListener` (ANTLR по умолчанию просто печатает в stderr — это нужно перехватить и превратить в структуру).
- Структура ошибки:
  ```rust
  pub struct SyntaxError {
      pub line: usize,
      pub column: usize,
      pub message: String,
  }

  pub struct ValidationResult {
      pub is_valid: bool,
      pub errors: Vec<SyntaxError>,
  }
  ```

### 1.3. Публичный API core-крейта
```rust
pub fn validate(sql: &str) -> ValidationResult;
pub fn validate_batch(sqls: &[&str]) -> Vec<ValidationResult>; // с rayon внутри
```

**Результат:** `cargo test` зелёный на базовом наборе (10–20 ручных запросов), крейт публикует `validate()`.

---

## Фаза 2. Тестовое покрытие (параллельно с Фазой 1, 1–2 недели)

- Взять/доделать набор ~150 валидных Trino/Iceberg конструкций (тот, что уже готовился отдельно).
- Добавить набор заведомо невалидных запросов (по одной ошибке на класс: незакрытая скобка, опечатка в ключевом слове, лишняя запятая, неверный порядок клauzes и т.д.) — минимум 30–50 штук.
- Оформить как `insta`/`rstest` snapshot-тесты или простые табличные тесты `#[test]`.
- Прогнать полный набор, зафиксировать baseline.

**Результат:** регрессионный набор, который защищает от поломок при рефакторинге/апдейте грамматики.

---

## Фаза 3. Python-биндинги (1–2 недели)

### 3.1. Структура проекта
```
trino-sql-core/     # чистый Rust
trino-sql-py/        # PyO3-обёртка, зависит от core
  Cargo.toml
  pyproject.toml      # maturin backend
  python/trino_sql_validator/__init__.pyi
```

### 3.2. PyO3-слой
```rust
#[pyfunction]
fn validate(sql: &str) -> PyResult<PyValidationResult> { ... }

#[pyfunction]
fn validate_batch(py: Python, sqls: Vec<String>) -> PyResult<Vec<PyValidationResult>> {
    py.allow_threads(|| {
        sqls.par_iter().map(|s| core::validate(s)).collect()
    })
}
```
- `#[pyclass]` для `PyValidationResult` и `PySyntaxError` с геттерами полей.
- Генерация `.pyi`-стабов вручную или через `pyo3-stub-gen`, чтобы в IDE была автодополнение/типизация.

### 3.3. Сборка
- `maturin develop` для локальной разработки.
- `maturin build --release` для продакшн-wheel.

**Результат:** `pip install .` работает локально, `import trino_sql_validator as tsv; tsv.validate("SELECT 1")` возвращает результат.

---

## Фаза 4. Производительность (1–2 недели, после того как всё функционально работает)

1. **Бенчмарки** (`criterion` в Rust, плюс `pytest-benchmark` на Python-уровне) на трёх категориях запросов: короткие (SELECT), средние (JOIN + WHERE), большие (CTE, DDL из Iceberg на сотни строк).
2. Профилирование (`cargo flamegraph` / `perf`) — найти, где реально уходит время: лексинг, построение parse-tree, обход ANTLR-рантайма.
3. Точечная оптимизация по результатам профиля, а не заранее вслепую:
   - Если узкое место — лексер: заменить на ручной лексер (`logos`), оставив ANTLR-парсер только для синтаксического дерева.
   - Если узкое место — аллокации в parse-tree: заменить владение `String` на `&str`-срезы, где возможно, добавить arena (`bumpalo`).
   - Если сам ANTLR-парсер целиком медленный — рассмотреть точечный переход на `lalrpop`/ручной recursive descent **только после** того, как есть regression-набор из Фазы 2, чтобы гарантировать эквивалентность поведения.

**Результат:** зафиксированные цифры (запросов/сек, p50/p99 задержка на запрос) + документ о принятых компромиссах.

---

## Фаза 5. CI/CD и дистрибуция (1 неделя)

- GitHub Actions (или внутренний CI) с `maturin-action`: сборка wheels для `manylinux`, `macos`, `windows` (x86_64 + arm64, если нужно).
- Прогон regression-тестов (Фаза 2) и бенчмарков (Фаза 4) на каждый PR.
- Публикация во внутренний PyPI/artifact-репозиторий.
- Semver-версионирование + changelog при обновлении грамматики под новую версию Trino.

---

## Фаза 6. Поддержка и обновление грамматики (постоянно)

- Процесс: при выходе новой версии Trino — обновить `.g4`, перегенерировать парсер, прогнать regression-набор, добавить тесты на новые синтаксические конструкции.
- Хранить маппинг "версия библиотеки → версия грамматики Trino".
