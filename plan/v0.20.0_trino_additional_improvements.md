# v0.20.0 — дополнительные улучшения проверки Trino SQL

## Статус и основание

План подготовлен 26 сентября 2026 года по предложению
[`Trinorust.md`](Trinorust.md). Проверена текущая реализация `0.19.0`,
commit `22f5d90` (`Add invalid datamart diagnostic coverage`).
Эта исходная точка сохранена в полях `baseline_v019` корпусов. Реализация
v0.20.0 подключила [100 тест-кейсов](../tests/cases/trino_483_grammar.json) к
pytest и добавила 84-cell composition matrix. Все labels повторно проверены
настоящим Trino 483; обычный тестовый прогон использует только сохранённые
ожидания и не требует Java.

Фактический результат реализации: стартовые 100/100 полных ожиданий проходят;
pinned positive audit достиг 484/484 statements, 238/238 expressions и 68/68
types; добавлены exact baseline identity, dev-only Java oracle, no-Python
Rust build, grammar inventory из 144 rules и три fuzz targets. P1 batch/GIL и
отложенные performance-работы V020-08/09 не реализовывались.

Из исходного документа стоит взять воспроизводимое сравнение с официальным
парсером, фаззинг и разделение Rust-ядра и Python-адаптера. Независимая
пакетная проверка SQL остаётся необязательным расширением. Предложение начать
проект заново с ANTLR не соответствует текущей зрелости библиотеки:
значительная часть описанного MVP уже реализована.

Главная цель версии — повысить точность и проверяемость существующего
Rust-native валидатора. Замена парсера, общая проверка типов/арности и
обязательное обращение к coordinator в эту версию не входят.

### Обязательная граница: лёгкая библиотека без Java

| Где | Допустимость JVM и грамматики |
| --- | --- |
| Установка локального wheel, импорт и все public API | JVM, ANTLR runtime, Java subprocess, coordinator, Docker и сеть не нужны |
| Сборка wheel и установка из sdist | Rust + Python build tools; без Java, Maven и генерации ANTLR в `build.rs` |
| Обычные Rust/pytest tests | Готовые SQL и ожидаемые результаты из корпуса; без JVM и сети |
| Разработка, обновление корпуса, отдельный audit job | Java разрешена для официального `trino-parser`; результаты фиксируются в файлах |

`SqlBase.g4` переиспользуется как спецификация для **построения тестов**, а не
как новый production backend. В wheel не включать JVM/JAR, generator,
Java harness или полную upstream-грамматику. Не добавлять их в Python runtime
dependencies. Offline-копия исходников для разработчика допустима; скачивание
и Java выполняются только явно вызванными dev-tools. «Лёгкая» здесь означает
сохранение Rust-native runtime без дополнительных тяжёлых зависимостей, а не
обещание неизменного числа байтов при добавлении новой функциональности.

### Уточнённые решения по результатам review

- TDD не обязателен. Порядок написания кода и тестов выбирается по удобству
  реализации; приёмка требует полного исполняемого покрытия и зелёного CI.
- Обязателен независимый audit через **Trino parser** в dev-окружении.
  Проверка через **Trino engine** нужна только для конкретных спорных SQL,
  не является отдельным этапом приёмки и не добавляется в runtime.
- Требование к движку — компилируемая реализация на Rust. Нет обязательных
  бенчмарков, профилирования, целевого ускорения или latency/throughput gate.
  Ограничения сложности и crash tests сохраняются как требования устойчивости.
- Приоритет — точное принятие/отклонение синтаксиса Trino 483, полная проверка
  вложенных фрагментов, сохранение warnings и исходных координат. Семантика
  типов, данных и разрешения объектов по-прежнему не входит в библиотеку.

### Поправки к техническим утверждениям исходного документа

1. **Грамматика не равна полному поведению парсера.** Trino после ANTLR
   запускает `PostProcessor` и `AstBuilder`. Это видно в
   [SqlParser Trino 483](https://github.com/trinodb/trino/blob/483/core/trino-parser/src/main/java/io/trino/sql/parser/SqlParser.java).
   Просто сгенерированное дерево может принять пустой quoted identifier,
   backticks или форму, отклоняемую при построении AST. Равенство 1:1 надо
   доказывать отдельным аудитом. Это ограничение уже отмечено в
   [плане v0.11](v0.11.0_SqlParser.md).
2. **ANTLR → Rust требует проверки конкретного toolchain.** Rust отсутствует
   в [списке targets ANTLR 4.13.2](https://www.antlr.org/download.html).
   Указанный в документе [antlr4rust](https://github.com/rrevenantt/antlr4rust)
   использует отдельный generator fork и runtime `antlr-rust`; обычной
   установки ANTLR недостаточно. В грамматике 483 есть `caseInsensitive` и
   Java-specific `isKeyword()` — нужны адаптация и тесты. Нельзя обещать
   обновление простым запуском генератора.
3. **Актуальный путь к грамматике** —
   `core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4`,
   а не предполагаемый путь внутри `trino-parser`.
4. **Java в `build.rs` усложнит установку из sdist.** Если когда-либо будет
   эксперимент с генерацией, его следует проводить отдельным dev-tool с
   фиксированными входами; обычная сборка wheel/sdist не должна требовать JVM.
   Копирование upstream-кода также требует сохранения его license/notice.
5. **`EXPLAIN` не является чистым syntax oracle.** Он требует анализа имён и
   доступных объектов. Для отдельного engine-аудита подходит
   [EXPLAIN (TYPE VALIDATE)](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/sql/explain.md)
   в подготовленной среде. `CATALOG_NOT_FOUND`/`TABLE_NOT_FOUND` не доказывают
   предполагаемую ошибку функции. `EXPLAIN ANALYZE` исполняет statement и для
   такой проверки не нужен.
6. **Для PyO3 0.29 использовать `Python::detach`.** Пример с `allow_threads`
   в исходном документе устарел относительно зависимости проекта; см.
   [руководство PyO3 0.29](https://pyo3.rs/v0.29.0/parallelism.html).
7. **Скорость не следует из выбора парсера.** Заявления о «максимальной
   производительности», резком выигрыше от arena или о lexer как основном
   узком месте не подкреплены профилем нашего кода. `sqlparser-rs` владеет
   своими AST-структурами; перевод их на arena/`&str` не является локальной
   заменой аллокатора. В этой версии такой performance-проект не выполняется;
   Rust-native архитектура не должна сопровождаться неподтверждёнными обещаниями скорости.
8. **Список всех ошибок — отдельный продуктовый контракт.** Recovery может
   порождать каскадные сообщения. Сейчас API возвращает одну ошибку; смена на
   `Vec<SyntaxError>`/`#[pyclass]` нарушит существующий контракт. Сохраняем
   первую ошибку каждого независимого input.

### 2.1. Подтверждённое ошибочное принятие WITHIN GROUP

```sql
SELECT sum(x) WITHIN GROUP (ORDER BY x) FROM t;
SELECT percentile_cont(0.95) WITHIN GROUP (ORDER BY x) FROM t;
SELECT custom_agg(x) WITHIN GROUP (ORDER BY x) FROM t;
SELECT "listagg"(x) WITHIN GROUP (ORDER BY x) FROM t;
```

Все четыре statements приняты текущей библиотекой; первый и четвёртый даже
не дают предупреждения. Нативный Trino 483 отвергает все четыре.
Его production `primaryExpression` разрешает `WITHIN GROUP` в специальной
форме с unquoted `LISTAGG`, но не в обычном `functionCall`.
Это grammar restriction, а не проверка существования функции.

Положительные контроли подтверждены обоими парсерами:

```sql
SELECT listagg(x, ',') WITHIN GROUP (ORDER BY x) FROM t;
SELECT custom_agg(x ORDER BY x) FROM t;
```

Последний statement остаётся синтаксически допустимым с `FunctionWarning`.
Qualified `s.listagg(x) WITHIN GROUP (...)` уже отвергается обоими парсерами;
его нужно сохранить как regression.

Связанный полный fixture:
`tests/fixtures/invalid_datamarts/mart_order_fulfillment_sla.sql`.
Сейчас тест фиксирует `valid=True` и предупреждения `percentile_cont`,
`decode`; после исправления правильным станет `valid=False`, одна ошибка
и пустой список warnings.

### 2.3. Baseline допускает возврат исправленных ошибок

В `plan/trino_483_audit_baseline.json` для positive statements сохранены восемь
`allowed_mismatches`, хотя в текущем прогоне осталось три. Пять устаревших IDs:

```text
positive_statements:1f69438035266f98
positive_statements:7eea2c574cd2771f
positive_statements:9d5cbd44b3173ec4
positive_statements:edf83b00c14abc79
positive_statements:fd6718febae203b1
```

`baseline_regressions()` проверяет `current - allowed`. Возврат ошибки с одним
из этих IDs не считается новым mismatch. Кроме того, upstream tool выводит
source hashes, но этот baseline не фиксирует их или полный состав case IDs:
проверяется revision и минимальное число cases. Замена одного извлечённого
case другим может сохранить denominator. SQLGlot baseline уже хранит hashes;
его подход можно переиспользовать.

Отдельная ошибка сравнения: `createExpression("1 + 1 x")` и
`createStatement("SELECT 1 + 1 x")` проверяют разные языковые формы. Второй
вариант допускает alias `x`; запрещать его в `validate()` нельзя.

### 2.4. Возможности улучшения устройства ядра

- `src/lib.rs::validate_input_complexity`, `empty_from_clause_location` и
  `trino_types::parse_sql` отдельно токенизируют исходный SQL;
  `statement_info` делает ещё один проход для `analyze_statements()`.
- Warning walkers и AST validators используют `to_vec()`/`clone()` над
  statements. Это кандидаты на устранение копий, но выигрыш ещё не измерен.
- Complexity guards сначала получают полный token vector. Ограничение числа
  значимых tokens не ограничивает размер одного literal/comment или расход
  памяти до проверки. Для metadata-пути также нужна проверка: после результата
  validation он запускается отдельно.
- `catch_unwind` переводит Rust panic в invalid result. Это полезно для API,
  но fuzz target поверх только этого wrapper может не заметить пойманную
  панику. Stack overflow/process abort этим механизмом не гарантированно
  перехватываются.

Повторная токенизация и копии AST не являются задачами оптимизации v0.20.0.
Работа над core в V020-05 нужна для тестирования и устойчивости, а не для
доказательства ускорения.

### 2.5. Что даёт SqlBase.g4 сверх существующего upstream-аудита

Проверена грамматика из чистого checkout Trino 483 на указанном выше SHA.
SHA-256 `SqlBase.g4`:
`dd7f545bd88187969453cd1544747ffcc0f788d02b38ce1f9da0c5e35638d184`.
В ней **144 parser rules**, **276 различных имён labelled alternatives**
(295 вхождений labels). Это инвентарь, а не denominator готового покрытия:
часть alternatives не имеет label, rules рекурсивны, сочетаний бесконечно много.

Выявлен дополнительный пробел extractor: `run_audit()` извлекает positive
expressions из вызовов `expression(...)`, но не из `createExpression(...)`.
Поэтому `testExtendedCase`, `testMatchPredicate`, `testUniquePredicate` не
попадают в прежние 238 expressions. Вызовы `rowPattern(...)` также требуют
собственной секции с правильным entry point. Следовательно, даже 238/238
не будут означать полного покрытия исходного `TestSqlParser.java`.

Отдельный файл [trino_483_grammar.json](../tests/cases/trino_483_grammar.json)
содержит 100 самостоятельно сокращённых examples и соседних boundary controls.
Каждый SQL прогнан отдельно через `SqlParser.createStatement` без внешней `;`
и через `validate(sql, dialect="trino", jinja="reject")`. JDK/JAR hashes,
правила грамматики, expected warnings с координатами, исходный commit и
фактические ошибки библиотеки записаны в корпусе. Expectations синтаксиса
получены от Trino, expectations warnings — из нашего catalog/API-контракта;
Java не проверяет warnings. Engine execution не проводилось.

| Семейство / IDs | Всего | Ошибочно отклоняет | Ошибочно принимает | Уже совпадает с Trino |
| --- | ---: | ---: | ---: | ---: |
| `WITHIN GROUP`, WG01–WG11 | 11 | 0 | 6 | 5 |
| Table functions, TF01–TF14 | 14 | 6 | 0 | 8 |
| SQL/JSON encoding, JE01–JE15 | 15 | 11 | 0 | 4 |
| `JSON_TABLE PLAN`, JP01–JP11 | 11 | 7 | 0 | 4 |
| Pattern windows, WP01–WP09 | 9 | 6 | 0 | 3 |
| Row patterns, RP01–RP19 | 19 | 10 | 1 | 8 |
| Остальные expression/boundary cases, GE01–GE21 | 21 | 9 | 0 | 12 |
| **Итого** | **100** | **49** | **7** | **44** |

Trino принимает **69** и отвергает **31** case. 56 расхождений — не 56
независимых дефектов: часть SQL — сокращения, вложения и диагностические
варианты одной проблемы. 44 совпадения нужны как ограничения для исправлений,
а не доказательство нового функционала. Полные совпадения строк с собранными
pytest parameters и literals в `tests/test*.py` не найдены, но это не доказывает
отсутствия эквивалентного теста. В `families.existing_tests` указано уже
существующее покрытие, которое нельзя считать новым.

Новые относительно первоначального плана подтверждённые пробелы:

- `MATCH_RECOGNIZE`: якорь конца раздела `$` ошибочно считается placeholder;
  не принимаются `INITIAL`/`SEEK`, `SKIP TO identifier`, пустой pattern `()`
  и некоторые неоднозначности contextual words. При этом `PATTERN (A**)`
  ошибочно принимается. Нельзя просто ослабить общий запрет `$1`.
- `CASE x WHEN <predicate fragment> THEN ...`: не принимаются, например,
  `WHEN BETWEEN ...`, `WHEN IS NULL`, `WHEN > ...`.
- `ROW(...) MATCH [UNIQUE] [SIMPLE|PARTIAL|FULL] (query)`, `UNIQUE (query)` и
  wildcard subscript `array[*]` не поддержаны. Это синтаксические конструкции,
  а не проверка уникальности данных или типов колонок.
- `JSON_TABLE PLAN DEFAULT` и отдельные positions `ENCODING` требуют tests
  сверх ранее найденных десяти полных upstream cases.

Важно не придумывать negative labels по внешнему виду. Native parser принимает
`A{4,2}` (семантика границ — другой слой), `SKIP TO FIRST PATTERN (A)` (`FIRST`
может быть обычным именем), `PERMUTE()` (contextual variable плюс empty pattern)
и `DESCRIPTOR()` в expression alternative table-function argument. Эти случаи
сохранены как positive syntax controls с пояснениями в JSON. Они не обещают
успешного выполнения в engine. Пустой quoted identifier, напротив, отвергается
PostProcessor, хотя лексическая форма присутствует в `.g4`.

### 2.6. Уточнённые ожидания диагностики

В schema v2 корпуса для всех 31 negative cases добавлены
`expected.error_location.anchors` и причина выбора точки ошибки. Labels SQL,
их тексты и исторические `observed_v019` не изменены. Якорь хранит точный
offset и текст проблемного token; несколько якорей допустимы только для
одного и того же дефекта. Например, незакрытая скобка может диагностироваться
по открывающей скобке или EOF, а не по произвольному месту запроса.

На текущем коде **44/100** по-прежнему совпадают по `.valid`, но **15** из
этих cases указывают на более раннюю допустимую конструкцию, а не на
ошибочный фрагмент. Типичный пример: invalid encoding отвергается на `FORMAT`,
поскольку валидная часть синтаксиса ещё не поддержана. После уточнения
координат полные ожидания выполняются в **29/100** cases. Эти 15 расхождений
диагностики дополняют 56 расхождений `.valid`; это не 15 новых независимых
семейств parser bugs. Подробный контракт и проверка преобразованных SQL — §13.

## 11. V020-08 — независимый batch и освобождение GIL (P1)

Предлагаемый добавочный Python API:

```python
def validate_batch(
    sqls: list[str] | tuple[str, ...],
    *,
    dialect: Dialect = "trino",
    jinja: JinjaMode = "auto",
) -> tuple[ValidationResult, ...]: ...
```

Контракт: `validate_batch(inputs, **options)` эквивалентен
`tuple(validate(sql, **options) for sql in inputs)` для корректных arguments.
Порядок результатов совпадает с input; invalid SQL не прерывает batch; каждый
input имеет свои budgets и function scope. Пустой список возвращает `()`;
options всё равно проверяются. В одном элементе разрешено то же multi-statement
SQL, что в `validate`; разные элементы не склеиваются через `;`.

- [ ] Проверить тип контейнера и всех элементов до native работы; одиночную
  строку, bytes и non-string elements отклонять как programming error.
- [ ] Сохранить Jinja preparation и dataclass conversion в тонком Python API,
  обновить `__all__`, native export и `_native.pyi`; формы существующих tuples
  не менять.
- [ ] Выполнять native core через `Python::detach`; обращения к Python objects
  и создание exceptions/results выполнять при attached interpreter.
- [ ] Первую версию batch сделать последовательной в Rust с одним detach.
  Rayon и управление workers оставить следующему performance-решению: короткие
  SQL могут не окупить создание задач, а внешние Python threads уже дают
  способ параллельного вызова после detach.
- [ ] Рассмотреть detach для `validate`, `validate_file`, `analyze_statements`;
  сохранить file/error semantics, не обещать измеренное ускорение.
- [ ] Проверить равенство полных результатов одиночного и batch API по всему
  corpus, Jinja modes, Hive/Generic, unknown options, Unicode positions и
  многоэлементным наборам с ошибками в начале/середине/конце.
- [ ] Проверить concurrency через bounded subprocess regression на отсутствие
  зависаний и недетерминизма. Не вводить speedup gate или хрупкий wall-clock
  assert в обычном pytest.
- [ ] Проверить ограниченность памяти крупного batch и документировать обработку
  caller-side chunks. Не вводить неограниченную materialization iterable API.

## 14. Что отложено

- Production ANTLR/Rust backend или объединение результатов двух парсеров.
  При необходимости — отдельный ограниченный prototype: toolchain pin,
  grammar actions, PostProcessor/AstBuilder parity, warnings, source locations,
  resource limits, wheel size, build time, throughput. Только после измерений
  можно обсуждать изменение текущего правила AGENTS «не vendor grammar».
- Semantic type/arity checker, обязательный `EXPLAIN` в `validate()`,
  автоматическая замена foreign functions. Это отдельные продукты/контракты.
- Много ошибок с parser recovery, новый публичный AST и смена dataclasses на
  `#[pyclass]`. Для текущих улучшений они не нужны.
- Переписывание корректных SQL fixtures, чтобы они начали давать warnings.
  Исходные допустимые конструкции из предыдущих обсуждений (`RANGE INTERVAL`,
  `TRUNCATE(x, d)`, `LISTAGG`, aggregate inside window) сохранять как positive
  controls. Нехватка аргумента известной функции остаётся engine-проверкой.
- Срок «4–6 недель» из исходного документа не использовать как оценку этого
  плана: это оценка другого, первоначального MVP без наших контрактов.

## 16. Итоговый объём работ, порядок реализации и приёмка

### Ожидаемый обязательный результат v0.20.0

| Блок | Что требуется выполнить | Как проверить завершение |
| --- | --- | --- |
| Архитектура поставки | Сохранить Rust-native runtime; Java только в явно запускаемом dev/audit tool | Установка wheel, сборка/установка sdist, импорт, public API и обычные tests работают без Java/Maven; wheel не содержит JAR/harness |
| Grammar inventory и audit, V020-01/02/10 | Карта 144 parser rules, provenance, исправление stale baseline, дополнительные entry points/extractor cases, воспроизводимый oracle | На изменённые/пропавшие cases и source hashes gate реагирует; crash/timeout не становится SQL error; у каждого правила указан статус |
| Syntax coverage, V020-03/04/07/10 | Закрыть семь семейств из §2.5: `WITHIN GROUP`, table functions, SQL/JSON encoding, JSON_TABLE PLAN, pattern windows, relation row patterns, дополнительные expressions | Все 100 стартовых cases проходят: 69 positive, 31 negative, точные warnings и допустимые error anchors; 49 false rejects, 7 false accepts и 15 ошибок локализации устранены |
| Regression suite | Подключить JSON к pytest, добавить Rust unit regressions, дополняющие alternatives и минимум 84 composition cells | Каждый SQL проверяется самостоятельно; нет skip/xfail на обязательных случаях; positive и negative neighbors проверены Trino; metadata и scopes сохранены |
| Устойчивость, V020-05 | Изолируемый core, fuzz targets, deterministic transformations, resource-limit tests | Production path и analysis не падают на сохранённых seeds; внутренние panics видны fuzz target; новые лимиты не вводятся молча |
| Rust-сборка и документы, V020-06 | Проверить wheel/sdist и native API без Java; обновить compatibility matrix и test counts | Реальная Rust extension устанавливается и работает; старые corpus targets 484/484 и 238/238 достигнуты; новые denominators показаны отдельно; benchmark не требуется |

Итого — **восемь обязательных этапов: V020-01–07 и V020-10**. Это расширение
текущего парсера и тестовой инфраструктуры, не перенос ANTLR runtime. В объём
не входят semantic type/arity checker, новая JVM-зависимость, перенос всей
грамматики в production, новый публичный AST и автоматическая правка SQL.
V020-08 (batch/GIL) — необязательная следующая очередь, не условие покрытия
этого релиза. V020-09 и обязательные performance measurements исключены из
объёма. Engine запускается только при спорном SQL, не для общей приёмки.

100 cases — зафиксированный стартовый корпус, а не максимальное число тестов.
84 composition cells могут частично пересекаться с ним и не прибавляются к
нему механически. Конечный прирост pytest/Rust cases следует посчитать после
генерации wrappers, ветвей и дедупликации. Полный охват всех комбинаций Trino
не обещается: непокрытые alternatives останутся видны в inventory/backlog.

### Рекомендуемый порядок работы без обязательного TDD

1. **Зафиксировать контракт и зависимости.** Использовать IDs и labels JSON,
   rule mapping и критерии §13/15. Выбрать shared parsing helpers там, где
   одинаковая грамматика используется relation/window или несколькими JSON forms.
2. **Реализовать удобными связными блоками.** Допустимы код сначала, тесты
   параллельно либо test-first. Не требуется отдельный RED-коммит или заранее
   падающий тест. Приоритет — точный разбор, сохранение metadata и простота
   поддержки; произвольное расширение Generic grammar запрещено.
3. **Подключить и дополнить все тесты.** Сверить IDs исходного корпуса с pytest,
   добавить Rust regressions, недостающие alternatives, wrappers, malformed
   neighbors и проверки координат. Неподтверждённые labels не выводить из
   результата нашей библиотеки; новые SQL сверять с native parser.
4. **Проверить через актуальную сборку.** После Rust изменений выполнить
   `maturin develop`. Проверить полный result, wrappers, inline scopes,
   `analyze_statements().validation`, Generic/Hive, budgets и fuzz seeds.
5. **Провести code review и финальную приёмку.** Проверить отсутствие потери
   вложенных выражений, ослабления грамматики и расширения allowlist ради pass.
   Все tests исполняются и проходят; завершённый этап не содержит скрытых
   skip/xfail. Выполнить полный CI-набор и Java-free wheel/sdist smoke.
6. **Обновить фактическую документацию.** Rule→test mapping, audit baseline и
   числа тестов обновлять после проверки результатов. Все обязательные критерии
   §15 должны выполняться; engine и бенчмарки не являются дополнительными gates.
   Release notes готовятся по факту; commit/tag/publish — отдельное действие.

Текущий срез расхождений можно воспроизвести **без Java** по сохранённым
labels (это диагностический прогон, а не замена будущим полным pytest assertions):

```bash
.venv/bin/python - <<'PY'
import json
from collections import Counter
from pathlib import Path
from trino_sql_validator import validate

corpus = json.loads(Path("tests/cases/trino_483_grammar.json").read_text())
counts = Counter()
for case in corpus["cases"]:
    result = validate(case["sql"], dialect="trino", jinja="reject")
    if result.valid == case["expected"]["valid"]:
        counts["syntax_match"] += 1
    else:
        kind = "false_reject" if case["expected"]["valid"] else "false_accept"
        counts[kind] += 1
        print(case["id"], kind, result.error)
print(dict(counts))
PY
```

Для проверенного v0.19.0 ожидается `syntax_match=44`, `false_reject=49`,
`false_accept=7`. Этот короткий пример проверяет только синтаксические labels;
15 ошибок локализации видны при сравнении с `error_location.anchors` (§2.6).
Критерий готовности v0.20.0 — **100/100 полных ожиданий**, а
не только отсутствие исключений или наличие любого warning. Java нужна лишь
для повторной независимой проверки labels, а не для этого тестового контракта.
