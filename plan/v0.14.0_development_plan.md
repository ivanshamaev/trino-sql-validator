# План разработки v0.14.0: полнота проверок и сохранение совместимости

Дата анализа: 2026-09-11.
База: `v0.13.0`, commit `ad7124a17b22dc80ff2dbe319920024fac0b58f4`, `main`.
Статус: выполнен. P0/P1 и opt-in P2 реализованы; версия 0.14.0 выпущена
коммитом и тегом `v0.14.0` (публикация в PyPI — по push тега).
Jinja/dbt выделен в [отдельный план](jinja_dbt_plan_dev.md) и дорабатывается отдельно.
При подготовке и уточнении документа исходники, тесты, fixtures и версии не изменялись.

## 1. Вывод

План `v0.11.0_SqlParser.md` выполнен в пределах зафиксированного набора проверок.
Все существующие тесты проходят, все 16 SQL-fixtures имеют явные ожидания.
Однако это не означает полного покрытия Trino SQL или полного обхода всех
функций и типов. Дополнительные проверки обнаружили воспроизводимые проблемы:

- завершение процесса на некоторых больших выражениях и SQL routines;
- пропущенные предупреждения в простых `ROW`, SQL/JSON, nested-column `ALTER`
  и statements под `EXPLAIN`/`PREPARE`;
- выход области видимости inline-функций за пределы их запроса;
- отказ корректным сочетаниям `WITH FUNCTION`/`WITH SESSION` и внешних statements;
- принятие чужого диалектного синтаксиса и некорректных форм `CALL`;
- отклонение допустимых `FOR VERSION AS OF <expression>` и идентификаторов;
- неполный каталог документированных типов и недостаточная автоматизация аудита.

Цель v0.14.0 — устранить эти дефекты и превратить измеренное покрытие в
воспроизводимый регрессионный контракт. Архитектура остаётся offline/Rust-native
на `sqlparser-rs`; семантический анализ координатора не добавляется.

Найденные проблемы Jinja-маскирования и новый template analysis API описаны в
[jinja_dbt_plan_dev.md](jinja_dbt_plan_dev.md). Они не входят в объём этого релиза.

Это направленные mutation probes, не измерение branch coverage или доказательство
полноты всех functions. В development-план включено превращение их в тесты.

### 2.2. Граница Trino / Iceberg / Hive / HDFS

Корпус охватывает SQL-формы работы с Iceberg и Hive. HDFS URL дополнительно
есть в `tests/test_trino_v483_coverage.py`, в кейсе
`hive_hdfs_external_location`; в самих fixtures используются преимущественно S3 URL.
HDFS — файловая система коннектора, отдельной SQL-грамматики HDFS здесь нет.
Наличие метастора, доступность пути, права, поддержка properties, корректность
snapshot/branch и возможность выполнения процедуры остаются вне offline syntax API.

В fixtures есть ожидаемо непроверяемые семантические проблемы: например,
`samples.sql` использует aliases `t`/`p`, отсутствующие в соответствующем `FROM`,
а `ddl_multi.sql` ссылается в `partitioned_by` на неописанную колонку.
Это не повод менять `valid=True` на синтаксически корректном SQL.
Источники: [Iceberg 483](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/connector/iceberg.md),
[Hive 483](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/connector/hive.md),
[HDFS 483](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/object-storage/file-system-hdfs.md).

## 4. Обязательный контракт совместимости

1. `validate()` / `validate_file()` сохраняют существующие defaults, тип результата,
   конструктор/сравнение/repr `ValidationResult`, поля и порядок warnings.
   Invalid SQL возвращает значение, а не exception и не аварийное завершение.
2. Пустые файлы остаются valid с `statement_count=0`; при ошибке в многооператорном
   файле сохраняются текущие `statement_count=0` и пустые warnings.
3. Неизвестные функции/типы остаются advisory: новые найденные warnings не меняют
   `valid`. Повторные реальные вхождения не объединяются; синтетические дубли
   одного исходного вхождения удаляются.
4. Сохраняются все 276 положительных fixture statements, 456 pinned Trino
   statements, 68 pinned type cases и поддержанные query/DDL/routine features.
   Исправление false accept может изменить результат для доказанно чужого или
   некорректного Trino SQL; каждое такое изменение описывается в changelog.
5. Усиление Trino не меняет поведение `hive`/`generic`; неизвестные connector
   procedures и plugin names не становятся синтаксическими ошибками по имени.
6. Каждый compatibility transform сохраняет source spans, literals/comments,
   nesting и принадлежность statement. Удалять неподдерживаемые токены для
   успешного разбора без валидации полной конструкции запрещено.
7. JVM, coordinator, Python SQL parser и subprocess не становятся runtime
   зависимостями. Изоляция subprocess допустима в development crash-тестах.
8. Сохраняется текущий регрессионный контракт Jinja modes и dbt fixture.
   Новый scanner, template API и изменение семантики маскирования относятся
   только к отдельному Jinja/dbt-плану и не блокируют v0.14.0.

### V014-01 — ограничить сложность разбора и исключить аварийное завершение

Приоритет P0. Файлы: `src/lib.rs`, `src/dialects/trino_types.rs`,
`src/dialects/trino_statements.rs`, отдельные subprocess integration tests.

Воспроизведено на локальном Linux с расширением 0.13.0:

```python
sql = "SELECT " + " + ".join(["1"] * 5000)
sql = ("CREATE FUNCTION f() RETURNS BIGINT " + "BEGIN " * 5000
       + "RETURN 1;" + " END;" * 4999 + " END")
```

Каждый вход проверялся в отдельном процессе с timeout 7 s и отключёнными core
dumps. Оба завершились с return code `-11` (`SIGSEGV`), примерно за 2.6–2.8 s,
вместо `ValidationResult`. Входы — около 20 KB и 55 KB. 4 000 сложений и
1 500 блоков в меньших probes проходили. Точный порог платформозависим.
Причину на уровне стека необходимо подтвердить диагностикой: текущий guard
ограничивает только вложенные скобки, а `catch_unwind` не перехватывает сигнал.

- [x] Добавить сначала изолированные regressions на эти два семейства, с timeout,
  проверкой normal exit и invalid-result при превышении документированного лимита.
- [x] Ввести общий budget глубины/сложности для token transforms, routines,
  parser recursion и AST processing; учитывать BEGIN/IF/CASE/loops и длинные
  AST-цепочки без скобок. Не ограничиваться общим числом символов SQL.
- [x] Проверить рекурсивные clone/visit/drop paths; убрать неограниченную рекурсию
  или обеспечить отказ до создания/обхода/освобождения опасного AST.
- [x] Проверить границы budget на валидных вложенных запросах, большом числе
  независимых statements и всех dialects; Trino-guards не прикрывают остальные.
- [x] Описать лимит и стабильную ошибку превышения; позиции возвращать, когда
  соответствующий исходный token известен.

Критерий: оба crash-reproducer нормально завершаются на Linux/macOS/Windows;
все существующие корректные fixtures проходят. Увеличение thread stack само
по себе не считается исправлением.

### V014-03 — сделать обход function/type metadata полным и независимым от fallback

Приоритет P1. Файлы: `src/lib.rs`, `trino_types.rs`, `trino_statements.rs`.

Следующие SQL сейчас valid, но нужного warning нет:

```sql
SELECT CAST(NULL AS ROW(x bignum));
SELECT CAST(NULL AS ARRAY(ROW(x bignum)));
SELECT json_array(1 RETURNING bignum);
SELECT json_value('{}', '$.x' RETURNING bignum);
SELECT * FROM JSON_TABLE('{}', '$' COLUMNS(x bignum PATH '$.x'));
SELECT bignum 'x';
DROP FUNCTION f(bignum);
PREPARE p FROM CREATE TABLE t(x bignum);
ALTER TABLE t ADD COLUMN payload.x bignum;
ALTER TABLE t ALTER COLUMN payload.x SET DATA TYPE bignum;
ALTER TABLE t ADD COLUMN x bignum WITH (value = missing_fn(1));
EXPLAIN ALTER TABLE t SET PROPERTIES value = missing_fn(1);
```

Также `SELECT CAST(1 AS INT64)` / `CREATE TABLE t(x STRING, y BYTEA)` не получают
type warnings: проверяется преимущественно `DataType::Custom`, тогда как
sqlparser знает встроенные типы других dialects. Это дефект name-checking,
а не основание отклонять Trino generic type name как плохой синтаксис.
`DECLARE x, y bignum` в routine даёт два одинаковых warnings на один type token.

Причины: `find_unknown_types` перечисляет часть statements/Expr вручную;
custom `ALTER` получает metadata через повторный Generic parse, который может
не удаться; простой ROW может быть принят до structural normalization;
metadata custom statements собираются преимущественно на верхнем уровне.

- [x] Сохранять декларации типов и выражения непосредственно при custom parsing,
  с исходным span/контекстом, без зависимости от успешного Generic replay.
- [x] Обходить все используемые type positions, включая простые и nested ROW,
  SQL/JSON RETURNING/COLUMNS, typed literals, DROP FUNCTION signatures,
  nested EXPLAIN/PREPARE, columns/defaults/properties и routine declarations.
- [x] Проверять исходное Trino type name также для sqlparser builtin variants;
  учитывать допустимые aliases, не выдавать warnings на synthetic STRUCT/NULL.
- [x] Не терять function expressions из custom metadata под wrappers;
  не считать procedure names обычными scalar functions.
- [x] Устранить synthetic duplicate warnings по идентичности исходного вхождения,
  сохранив повторные отдельные вызовы/типы и сортировку по source position.
- [x] Добавить invariant: перенос одинакового выражения/типа в поддержанный
  контейнер или другой statement не теряет warning и не создаёт дубль.

Критерий: все примеры получают ровно положенные advisory warnings, оставаясь
valid; проверены точные координаты и все 65 VARCHAR mutations reports schema.

### V014-04 — композиция query prefixes и область видимости inline functions

Приоритет P1. Зависимость: согласовать ownership metadata с V014-03.

Матрица из 57 допустимых сочетаний (10 query families × wrappers с учётом
ограничений grammar) дала 50 проходящих и 7 отказов:
`WITH FUNCTION` не работает под EXPLAIN, PREPARE, CTAS, CREATE VIEW, INSERT;
`WITH SESSION` — под EXPLAIN/PREPARE. CORRESPONDING, PIVOT, NEAREST, row expansion,
GROUP BY ALL, nested ROW, JSON_TABLE и MATCH_RECOGNIZE SUBSET прошли каждый
во всех шести контекстах.

```sql
CREATE TABLE t AS
WITH FUNCTION f(x BIGINT) RETURNS BIGINT RETURN x SELECT f(1);

WITH FUNCTION local_probe(x BIGINT) RETURNS BIGINT RETURN x
SELECT local_probe(1);
SELECT local_probe(2); -- сейчас warning ошибочно отсутствует
```

- [x] Применять prefix parsing на допустимых grammar query roots, включая
  statements под wrappers; учитывать различие `rootQuery` и
  `rootQueryWithSession`, не разрешая WITH SESSION везде автоматически.
- [x] Привязать inline declarations к конкретному query scope; убрать глобальное
  множество имён на весь файл.
- [x] Проверить unqualified local calls, qualified calls, взаимные вызовы,
  CTE/subqueries и следующие statements; `remote.ns.local_probe()` не должен
  считаться локальной функцией только из-за совпадения последней части имени.
- [x] Покрыть expression/compound/dollar bodies, несколько declarations и
  сочетание WITH SESSION → WITH FUNCTION → WITH CTE, с позициями warnings.

Критерий: все 57 корректных сочетаний проходят; local exemption заканчивается
на границе своего query и не скрывает unknown functions в соседнем statement.

### V014-05 — строгая структура CALL и ALTER ... EXECUTE

Приоритет P1; закрывает первый пункт Next в roadmap.
Основные источники: [CALL 483](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/sql/call.md)
и правила `call`, `argument`, `tableExecute` закреплённой grammar.

Сейчас ошибочно valid:

```sql
CALL system.register_table;
CALL system.register_table(DISTINCT 1);
CALL system.register_table(*);
CALL system.register_table(1) FILTER (WHERE TRUE);
CALL system.register_table(1) OVER ();
ALTER TABLE t EXECUTE system.optimize();
ALTER TABLE IF EXISTS t EXECUTE optimize();
```

- [x] Реализовать/проверить CALL production: qualified procedure name, обязательные
  скобки, пустой либо positional/named expression list, полное потребление.
- [x] Исключить aggregate/window decorations и wildcard arguments; проверять
  `=>`, commas, closing delimiter и trailing tokens.
- [x] Для ALTER TABLE EXECUTE соблюдать отдельные правила procedure identifier,
  допустимых префиксов и optional WHERE, сохраняя уже поддержанный MV EXECUTE.
- [x] Добавить connector matrix: существующие rollback/register/sync_partition
  и optimize/expire/remove_orphan плюс документированные Hive/Iceberg формы
  из syntax matrix; nested function/type warnings в argument values и WHERE.
- [x] Явно описать contract: procedure name/набор доступных параметров/arity/
  типы/права/connector capability не проверяются. `CALL system.custom_proc()`
  остаётся синтаксически valid без искусственного FunctionWarning.

Критерий: все 4 fixture CALL и 16 optimize statements reports fixture остаются
valid, перечисленные malformed формы отвергаются, выражения аргументов обходятся.

### V014-06 — закрыть подтверждённые утечки Generic grammar и ошибочные guards

Приоритет P1. Файлы: dialect delegates, statement hooks, token/AST guards.

Сейчас принимаются SQL-формы, отсутствующие в соответствующих Trino 483 productions:

```sql
CREATE INDEX idx ON t(x);
SELECT x FROM t QUALIFY row_number() OVER () = 1;
SELECT 1 LIMIT 1 + 2;
SELECT 1 LIMIT 1, 2;
UPDATE t SET x = 1 FROM s WHERE t.id = s.id;
DELETE FROM t USING s WHERE t.id = s.id;
INSERT INTO t VALUES (1) RETURNING *;
SELECT 1 <=> 1;
SELECT 'a' ILIKE 'A';
SELECT * FROM arbitrary_name(1);
ALTER TABLE t ADD COLUMN x BIGINT DEFAULT missing_fn(1);
```

Последний пример важен: Trino column DEFAULT production требует literal;
непроизвольные literal defaults из Iceberg fixture сохраняются. Не следует
переносить это ограничение на routine defaults, где правила другие.

Есть и ложный отказ: `SELECT * FROM offset`, `SELECT * FROM limit`,
`SELECT substring('abc' FROM offset)` и `SELECT trim('x' FROM offset)`.
`LIMIT`/`OFFSET` входят в Trino nonReserved, но `has_empty_from_clause`
отклоняет их по соседним токенам без учёта контекста.

- [x] Зафиксировать перечисленные примеры как grammar-backed positive/negative
  regressions и проверить соответствующие GenericDialect hooks/AST variants.
- [x] Ограничить Trino statement/clause/operator surface там, где делегирование
  пропускает конструкции другого dialect; применять проверки контекстно.
- [x] Заменить глобальный FROM/keyword guard на проверку relation context с
  корректной таблицей reserved/nonReserved и возвращением source location.
- [x] Добавить negative neighbors из actual fixtures для LIMIT, DML, table
  functions и DEFAULT; одновременно защитить aliases, strings/comments и
  именованные параметры с совпадающими словами.
- [x] Сохранить NAME-based advisories, не вводить семантический whitelist
  function arguments или connector properties.

Критерий: перечисленные false accepts отвергаются только в Trino, допустимые
nonReserved identifiers принимаются, fixture и pinned positive gates неизменны.
Источник для классификации: [Trino 483 grammar](https://github.com/trinodb/trino/blob/483/core/trino-grammar/src/main/antlr4/io/trino/grammar/sql/SqlBase.g4).

### V014-07 — дополнить time travel и проверить type/query composition

Приоритет P1. Файлы: `trino_types.rs`, targeted query/type regressions.

Сейчас отклоняются корректные по `queryPeriod` формы:

```sql
SELECT * FROM t FOR VERSION AS OF CAST(1 AS BIGINT);
SELECT * FROM t FOR VERSION AS OF (1);
SELECT * FROM t FOR VERSION AS OF ?;
SELECT * FROM t FOR VERSION AS OF 1 + 2;
```

`FOR TIMESTAMP AS OF missing_fn(1)` уже сохраняет warning; VERSION path более узок.
Обнаружена также неодинаковая поддержка postfix type: `bignum ARRAY` проходит
в CAST, но не в `CREATE TABLE t(c bignum ARRAY)`.

- [x] Разбирать полный `valueExpression` queryPeriod с корректной границей
  alias/JOIN/WHERE/ORDER, сохраняя metadata выражения и позицию.
- [x] Покрыть placeholders, арифметику, CAST, parentheses и nested functions,
  malformed neighbors и уже работающие numeric/string branch versions.
- [x] Проверить type-form matrix в CAST/columns/ALTER/function signatures,
  включая unknown-name postfix arrays; устранить подтверждённые различия
  контекстов, сохраняя TypeWarning вместо semantic rejection.

Критерий: корректные grammar forms проходят во всех заявленных контекстах;
unknown function/type warnings остаются non-fatal и расположены на исходном SQL.

### V014-08 — полный и воспроизводимый function/type catalog

Приоритет P1. Файлы: `tools/extract_functions.py`, `tools/extract_types.py`,
генерируемые каталоги и тесты генераторов.

Новых пропущенных scalar function names в выбранных 37 function-doc files не
найдено: все 470 имён совпали. Это не доказывает полноту типов или всех источников.
`Geometry`, `SphericalGeography`, `BingTile` документированы в
[geospatial functions](https://github.com/trinodb/trino/blob/483/docs/src/main/sphinx/functions/geospatial.md),
но `SELECT CAST(NULL AS Geometry)` и аналоги сейчас выдают ложные TypeWarning.
Извлечение только headings из `language/types.md` их не видит.

Генераторы по умолчанию читают moving master, не записывают source SHA/hash;
function generator может перезаписать полный каталог после частичной загрузки
документации. Тестов на эти development tools сейчас нет.

- [x] Включить подтверждённые documented SQL types из дополнительных источников;
  отличать реальные SQL type names от обозначений Point/Polygon в signatures.
- [x] Добавить `--ref`/resolved SHA, source manifest/checksums и `--check` для
  read-only проверки drift; офлайн builds используют committed catalog.
- [x] Не записывать новый каталог при неполной загрузке обязательных источников
  или ошибке разбора; подготовить весь результат до атомарного обновления.
- [x] Тестировать aliases, case folding, missing docs, malformed input,
  deterministic ordering и reproducible generation без сети.
- [x] Пересмотреть hard-coded special names (`TABLE`, `DESCRIPTOR`, pattern
  navigation): различать syntax node и функцию; не вводить context-semantic
  errors вроде проверки допустимости PREV вне MATCH_RECOGNIZE в syntax API.

Критерий: обычные documented geotypes не дают warnings, опечатки дают;
получение одного и того же pinned source воспроизводит один и тот же каталог;
неполный источник никогда не уменьшает committed catalog молча.

### V014-11 — statement metadata как opt-in public API

Приоритет P2, после исправлений P0/P1; закрывает второй пункт Next roadmap
в части statement kinds/indexes. Не является условием исправления critical bugs.

Сейчас `ValidationResult` содержит только aggregate outcome.
`ParsedSql.custom_statement_kinds` — отдельный список subset kinds, без общего
индекса и span; custom statements всё ещё могут иметь `Statement::Commit`
placeholder. Нельзя выводить public kind из такого AST без коррекции.

- [x] Создать внутреннюю запись для каждого statement: index, исходный span,
  собственный kind, wrapper/inner kind при необходимости и связанная metadata.
  Routine semicolons не делят такую запись на независимые statements.
- [x] Добавить отдельный opt-in `analyze_statements()` с типизированным result,
  содержащим прежний `ValidationResult`, tuple `StatementInfo` и error-statement
  index при известной границе; окончательный API зафиксировать тестом контракта.
- [x] Оставить поведение, сигнатуры и dataclass equality существующих validate
  APIs неизменными; не менять существующую native tuple shape ради нового API.
- [x] Добавить native entry point, `.pyi`, Python types, exports, docs и tests
  для SELECT/DDL/DML/CALL/session, custom DDL, EXPLAIN/PREPARE и invalid scripts.

Критерий: kinds определяются по исходному statement, не по placeholder;
старые API regression tests проходят без изменений ожиданий.
`allow_ddl=False` отложить до отдельного policy-контракта: это не read-only
гарантия, поскольку INSERT/UPDATE/DELETE/CALL и ALTER EXECUTE требуют разных
правил. Такой флаг не следует незаметно смешивать с синтаксической валидностью.

## 6. Последовательность и критерий готовности

1. V014-00 baseline и минимальные reproduction tests для найденных дефектов.
2. V014-01 — process safety; Jinja/dbt выполняется по отдельному плану и не
   блокирует следующие этапы SQL parser.
3. V014-03/04 — единая metadata и scopes, затем V014-05/06/07 parser fidelity.
4. V014-08/09 — каталоги и upstream gate; V014-10 — interaction regressions.
5. V014-11 — opt-in metadata при включении P2; V014-12 — документация и release checks.

v0.14.0 готов, когда P0/P1 этого плана завершены (V014-02 исключён), каждый
подтверждённый пример из текущего объёма имеет
регрессионный тест, ни один ожидаемо-valid fixture не сломан, не появилось новых
неклассифицированных pinned mismatches и smoke tests не завершают процесс сигналом.
Число новых tests не является критерием само по себе: важны конкретные assertions
на syntax, scope, warnings, coordinates и normal process exit.

Изменения выдачи warnings допускаются только для описанных дефектов и с явными
ожиданиями; исправления синтаксиса проверяются против закреплённого upstream.
Переход на другую версию sqlparser/Trino или массовая перепись parser pipeline
не совмещаются с этим релизом без отдельного анализа регрессий.
