# v0.7.0 Plan: reported recursive Trino queries

## Analysis

The four reported examples fail for syntax around recursive queries, but not
because recursive CTEs are fundamentally unsupported by the pinned
`sqlparser 0.62`:

- Top-level and nested `WITH RECURSIVE` CTEs already parse when their types use
  sqlparser's `ARRAY<type>` spelling.
- Trino permits `ARRAY(VARCHAR)` and `ARRAY(BIGINT)` in cast type positions;
  sqlparser expects angle brackets and reports `Expected: <, found: (`.
- The second query uses `top` as an implicit subquery alias. `TOP` is reserved
  by the generic dialect, although Trino permits it as an identifier in this
  alias position.
- The fourth query combines nested recursive CTE syntax with
  `ARRAY(BIGINT)`, so its reported recursive error is a downstream parse error
  from the unsupported type spelling.

## Implementation

- Normalize simple Trino `ARRAY(type)` type forms to the equivalent
  `ARRAY<type>` parser form while preserving the original character offsets.
- Permit `TOP` as a table alias in the Trino dialect only; leave other dialects
  unchanged.
- Do not rewrite or special-case `WITH RECURSIVE`; preserve sqlparser's native
  recursive CTE AST and scope handling.
- Add inline regression tests for all four reported query shapes. The original
  examples are intentionally not stored in the repository.

## Verification

Run `cargo fmt --check`, `cargo test`, `cargo clippy --all-targets -- -D warnings`,
`pytest -q`, `ruff check .`, and `mypy python/trino_sql_validator`.

## Follow-up

If production examples still fail after these changes, reduce each failure to
its smallest syntax feature and add a focused inline regression test before
expanding the dialect. Avoid blanket normalization of all recursive SQL or
loosening the generic dialect.
