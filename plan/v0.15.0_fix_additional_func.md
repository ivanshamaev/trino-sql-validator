# v0.15.0 — add hidden Trino functions `fail` and `combine_hash` to the catalog

## Проблема

Основная часть каталога функций (`src/functions.rs`) извлекается из
`docs/src/main/sphinx/functions/` в `trinodb/trino`, а отдельные исключения
заданы в `SPECIAL_FUNCTIONS`. Анализ исходников Trino показал ещё две
**скрытые** (hidden) функции, которые реально работают в Trino, но не попадают
ни в документацию, ни в `SHOW FUNCTIONS`, ни в текущий список исключений:

| Функция | Файл в Trino | Примечание |
|---|---|---|
| `fail(...)` | `operator/scalar/FailureFunction.java` | вызывает `TrinoException` из SQL; используется в тестах/отладке |
| `combine_hash(bigint, bigint) -> bigint` | `operator/scalar/CombineHashFunction.java:27` | `@ScalarFunction(value = "combine_hash", hidden = true, neverFails = true)`; внутренний хеш для GROUP BY / JOIN; в docs встречается только в выводе планов (`sql/explain.md`) |

Сейчас валидатор выдаёт ложный warning «unknown function» на запросы,
использующие эти функции:

```sql
SELECT fail('boom');                         -- warning: unknown function `fail`
SELECT combine_hash(1, 2);                   -- warning: unknown function `combine_hash`
```

Это ложноположительное срабатывание (false positive): SQL валиден в Trino.

## Решение

Механизм уже существует: `tools/extract_functions.py` содержит множество
`SPECIAL_FUNCTIONS` — имена, добавляемые к извлечённым из документации
(`current_date`, `grouping`, `json_query`, ...). Именно для таких случаев
(функции без директив `:::{function}` в docs) он и заведён. Достаточно
добавить два имени и перегенерировать каталог — вручную `functions.rs`
править нельзя (`@generated`).

## Шаги

1. **`tools/extract_functions.py`** — добавить в `SPECIAL_FUNCTIONS`:
   ```python
   "combine_hash",
   "fail",
   ```
   (алфавитный порядок; имя `fail` не конфликтует с зарезервированными
   словами и корректно распознаётся `find_unknown_functions` по последнему
   `Ident` из `ObjectName`).

2. **Перегенерировать каталог** (нужен доступ к docs по сети):
   ```bash
   python tools/extract_functions.py --ref 483
   python tools/extract_functions.py --ref 483 --check   # или CI
   ```
   В `src/functions.rs` в сортированный список добавятся `"combine_hash"` и
   `"fail"`. В `src/functions.manifest.json` значение `entry_count` изменится с
   470 на 472; checksum исходных документов не изменятся, поскольку новые имена
   добавлены из `SPECIAL_FUNCTIONS`. Если `--ref 483` недоступен — каталог и
   manifest следует обновить согласованно вручную, сохранив сортировку, а при
   следующей регенерации diff обязан быть пустым.

3. **Версия** — поднять в `Cargo.toml` `[package] version` до `0.15.0` и
   синхронно в `pyproject.toml` `[project] version` (single source of truth —
   Cargo, но оба должны совпадать). Обновить `CHANGELOG.md`.

4. **Тесты** (`tests/`):
   - `tests/test_validator.py` —
     добавить кейсы:
     ```python
     def test_hidden_fail_function_no_warning():
         r = validate("SELECT fail('boom')", dialect="trino")
         assert r.valid and r.warnings == ()

     def test_hidden_combine_hash_no_warning():
         r = validate("SELECT combine_hash(1, 2)", dialect="trino")
         assert r.valid and r.warnings == ()
     ```
     и негативный контроль — по-прежнему незнакомое имя (`failx(`) даёт
     warning.
   - Если есть sql-фикстуры в `tests/fixtures/` — не требуется, инлайн
     достаточно.

5. **Проверка**:
   ```bash
   maturin develop
   cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
   pytest -q && ruff check . && mypy python/trino_sql_validator
   python tools/extract_functions.py --ref 483 --check
   ```

## Что не делаем и почему

- **Не расширяем проверки до arity/типов** (`fail(varchar, ...)` имеет
  перегрузки) — валидация сигнатур остаётся out of scope (см. README и
  `plan/functions-validation.md`).
- **Не добавляем общий механизм чтения Java-аннотаций**
  `@ScalarFunction(hidden=true)` в `tools/extract_functions.py`: в Trino есть
  и другие hidden-аннотации, но среди них встречаются SQL-конструкции,
  документированные функции и внутренние `$...`-имена. Для исправления двух
  конкретных пропусков Java-парсер и правила классификации неоправданно
  усложнят генератор. Если понадобится полный аудит скрытого API, его следует
  спланировать отдельно по всему `trino-main`, а не только по
  `operator/scalar/`.
- **Не документируем эти функции в README** как поддерживаемые отдельно —
  они просто перестанут давать warning, поведение консистентно с остальным
  каталогом.

## Риски

- `fail` — обычный идентификатор; в редких схемах может быть колонкой/таблицей
  с именем `fail`. Коллизий с вызовом функции это не создаёт: walker
  проверяет только `Expr::Function`.
- `combine_hash` может не существовать в старых версиях Trino (появился с
  внутренней миграцией хешей) — но каталог генерируется от pinned `--ref 483`,
  поведение по умолчанию «валидно для 483».
- Каталог проверяет только имя, поэтому не различает встроенные и одноимённые
  plugin-функции. Это соответствует существующему контракту name-only
  validation и не меняет валидность SQL.
